# Cronsole

Cronsole is a **single pane of glass** for scheduled tasks across Windows Task Scheduler,
Claude Code Routines, and Cronsole-native HTTP jobs. It is **local-first by design** — the
frontend, backend, and agent all run on the user's own machine. There is no hosted/SaaS
instance; the Hetzner control-plane plan was dropped 2026-07-13.

**Read this first, then read the canonical doc for the area you're touching.** This skill is
a mental model, a set of invariants, and a routing table — **not** a copy of the docs. When
this skill and a repo doc disagree, **the repo wins**; fix the skill.

## The one thing to understand

Cronsole is a **reliability control plane**. Its entire value is that the state it shows is
*true* and the actions you take *actually happen*. That reframes what counts as a bug:

> **A confident lie is the worst possible failure.** A dashboard that reports success for a
> run that never happened is worse than an error, worse than a crash, worse than no dashboard
> at all. When you must choose between a graceful degradation and an honest refusal, **choose
> the honest refusal.**

This is why `task:delete` only removes the DB row *after* the platform confirms; why an
admin-ACL'd task returns "needs elevation" instead of a fake success; why lossy schedule
conversion surfaces a warning instead of quietly degrading; and why a declared-but-uncompiled
target offers "copy to set up manually" rather than silently no-op'ing.

## Architecture at a glance

Four long-running processes plus Redis, and an on-demand `mcp-server` your AI host launches.
The **agent always dials out** — the server never connects in.

```
┌─ Frontend ──┐  REST/JWT + Socket.io   ┌─ Backend ──┐   Prisma    ┌──────────┐
│  React 19   │ ──────────────────────► │  Express 5 │ ──────────► │ Postgres │
│  :7373      │                         │  :3000     │             │  :5432   │
└─────────────┘                         └──────┬─────┘             └──────────┘
                                        ▲  ▲   │  HTTP (sha256-verified)
┌─ MCP host ──┐  MCP/  ┌────────────┐   │  │   └──────────────► Registry / Webhooks
│ Claude/Codex│ stdio  │ mcp-server │   │  │
│   Cursor    │ ─────► │ REST+Bearer│ ──┘  │
└─────────────┘        └────────────┘      │ WS + HMAC (outbound only)
                                    ┌──────┴─────┐   COM    ┌──────────────────┐
                                    │ .NET Agent │ ───────► │ Win Task Sched.  │
                                    │ host .exe  │          └──────────────────┘
                                    └────────────┘
```

The agent is a **client, not a server** — it never binds `0.0.0.0`. It can't be
containerized because it needs Task Scheduler COM access, which is why it's a host process
and why it **never hot-reloads** (see Traps).

The **`mcp-server` is a peer of the frontend, not a layer of its own** — another REST client
holding a bearer token. That's the whole design: it owns **no logic**, so every guarantee
(owner scoping, no-shell `exec`, signed agent commands, cron→trigger conversion) stays in the
backend where it's already tested. A tool that needs new behavior needs a **backend route**,
not cleverness in `mcp-server/`.

Details: [references/architecture.md](references/architecture.md)

## The two AI surfaces — don't conflate them

Cronsole has two, with different audiences and lifecycles. Most confusion here starts with
mixing them up:

| | **This skill** (`skills/cronsole/`) | **The MCP server** (`mcp-server/`) |
|:---|:---|:---|
| Audience | An agent **working on** Cronsole's codebase | An agent **using** a running Cronsole |
| Surface | `SKILL.md` + `references/` | 15 tools over MCP/stdio |
| Needs | Nothing — it's just text | A running backend + a user JWT |
| Canonical doc | [`skills/README.md`](../README.md) | [`docs/user-guides/guides/MCP_Server_Guide.md`](../../docs/user-guides/guides/MCP_Server_Guide.md) |

A third thing shares the name and is neither: the **dev-tooling MCP servers** in the root
`.mcp.json` (context7, playwright, serper, …) that help you *build* Cronsole. That file holds
**both** — the dev tooling *and* a `cronsole` entry pointing at this repo's own product server.
The `cronsole` entry is the only one needing a backend and a token, so it's the only one that
can fail to start.

**The 15 tools**, each mapping 1:1 onto a backend route (details, wiring, token minting:
[MCP_Server_Guide.md](../../docs/user-guides/guides/MCP_Server_Guide.md)):

| Tier | Tools |
|:---|:---|
| **Read** | `list_tasks`, `list_templates`, `list_folders`, `get_task_history`, `export_task`, `convert_schedule`, **`list_platforms`** (the capability matrix — call it before planning anything you are unsure is possible; `unsupported` is a boundary, not a to-do), **`get_task_health`** (`unknown` ≠ `ok`), **`list_run_history`** (cross-task; rows are runs *Cronsole performed*, and each carries `runKind`), **`list_claude_routines`** |
| **Create** | **`create_task`**, `create_native_task`, **`create_native_script_task`** (runs a program on the *backend host* — the container on a Dockerized install), `create_task_from_template` (all take `folder`; `create_task` alone also takes **`createFolder`**, default false — see the folder invariant below) |
| **Act** | `run_task` |
| **Modify** (reversible) | `set_task_status`, `update_task_schedule`, `update_task_action` (Windows), **`update_native_job`** (Cronsole-native job spec — **replaces**, never merges, since the two job types share no fields), **`rename_task`** (a Cronsole label only — the platform is untouched, `externalId` unchanged; survives sync), **`untrack_task`** (removes the task from Cronsole, **leaves the platform entry running**; refuses `TASKHUB_NATIVE` **and `CLAUDE_CODE`**, whose rows *are* the task), **`sync_tasks`** (omit `categories` = refresh, adds nothing new; passing them = import, and that also forgets prior untracks inside them) |
| **Create / connect** (Claude) | **`create_claude_routine`** makes a real routine (name · prompt · UTC cron · optional repos/tools) — it needs a readable Claude Code session on the backend's machine, so **check `list_claude_routines` → `session.mode` first** (`oauth` = available, `declared` = tell the user to run `/login`, or create at claude.ai and connect). **`connect_claude_routine`** / **`edit_claude_routine`** / **`disconnect_claude_routine`** remain for the declared path. Connect takes a **live credential as a parameter**, so it lands in the host transcript; prefer the UI when a human is present. Re-connecting an id **replaces** the token (that is the rotation path), while **`edit_claude_routine` keeps it** — fixing a mistyped id must not cost a credential, since claude.ai shows a token once; the tracked task follows the id so its history and star survive. Disconnect is not a delete: the routine keeps running at claude.ai, and the discarded token cannot be recovered. **There is no `delete_claude_routine` and cannot be** — neither Claude API exposes a DELETE (verified by enumerating the surface). Park a routine with `set_task_status`; removing it happens at claude.ai. *(The "deliberately no `create_claude_routine`" note that stood here until 2026-08-13 was true of the documented API and false of the product — see [#50](../../docs/troubleshooting/README.md#50-two-claude-routines-apis-and-the-documented-one-is-the-smaller-one).)* |
| **Destroy** (gated, and **native-only**) | `delete_task` → **`DELETE /api/tasks/:id/native`**, not `DELETE /api/tasks/:id`. Refuses every platform but `TASKHUB_NATIVE` with a **400**, Windows included — so **no MCP verb can destroy an artifact on the machine**; Windows removal over MCP is `untrack_task`. The backend **archives the definition + last 20 runs before deleting** and **refuses the delete if the archive write fails** (task left unchanged); read them back at `GET /api/tools/task-archives[/:id]`. Registered **only** when `CRONSOLE_MCP_ALLOW_DESTRUCTIVE=true`; otherwise **absent from `tools/list`**, not present-and-erroring. |
| **REST-only** (no MCP tool) | bulk export `POST /api/tools/export/tasks` (`scope: all \| folder \| selection`), **restore `POST /api/tools/restore/tasks`**, the three bulk verbs — **enable/disable `POST /api/tools/tasks/status`**, **recategorize `POST /api/tools/tasks/category`**, **untrack `POST /api/tools/tasks/untrack`** — **analytics `GET /api/tools/analytics`**, **favorites `POST` / `DELETE /api/tasks/:id/favorite`** (the `isFavorite` flag rides on `GET /api/tasks`; `compactTask` does not forward it, so `list_tasks` cannot see stars), connect-pack downloads `GET /api/tools/downloads[/:id]`, plus template import/export, save-as-template, pairing. **The bulk verbs are omitted on purpose, not pending**: friction has to scale with blast radius, and the UI earns that with a typed confirmation past 25 tasks (`TYPE_TO_CONFIRM_THRESHOLD`). An MCP tool has no such gesture, so a bulk untrack of 254 tasks would arrive with less deliberation than the single-task path — the gap the Mass Actions console exists to close. |

**The gating is tiered, and the tiering is the point** (decided 2026-07-15). Irreversible is
gated; reversible is not. `set_task_status` ships ungated *on purpose*: it is the honest way to
park a task, and gating it would push you toward cronning a task into silence — which is trap
#14 exactly. **A gate that makes the safe path harder than the unsafe one is worse than no gate.**
The gate is an **env var, not a `confirm: true` param**, because a param is filled in by the
model — the caller assuring itself it's sure, which is the missing deliberation, not a substitute
for it. `untrack_task` (2026-07-28) is the same argument applied to *removal*: gating deletion is
only honest once a **safe** way to remove a task from the dashboard exists ungated — otherwise an
agent asked to "clean this up" has one tool for the job and it's the irreversible one.

**Still REST-only:** template import/export, save-as-template, sync, agent pairing, **favorites**
(`POST` / `DELETE /api/tasks/:id/favorite`). If a user asks for one over MCP, say the tool doesn't
exist and offer the REST call or the UI — **never improvise a substitute.**

**Creating a task on a real machine? Read
[references/task-authoring.md](references/task-authoring.md) first** — the creation paths,
command recipes per kind of work (script / exe / shell opt-in / HTTP / CLI agent), the
quoting and folder rules, and how to verify a task actually ran.

## Non-negotiable invariants

Violating any of these is a bug even if every test passes. Most are load-bearing for either
security or honesty.

| Invariant | Why it exists |
|:---|:---|
| **All schedules stored as 5-field cron in UTC** | Storing local time is a whole bug class (wrong-time runs, DST drift). This is the storage, REST, signed-command and MCP contract — **it does not move**. |
| **The user's timezone lives at the browser's edge and nowhere else** | Cron *fields* read and accept `settings.timezone` (an IANA id, default **`America/Los_Angeles`**); `useScheduleZone().toUtc()` runs **once, on submit**. A zone that reached storage would fork the meaning of every cron in the DB by author, and `create_task` has no access to a browser preference — so the machine surface stays unambiguously UTC and only the human surface converts. Every shifted field prints the stored UTC form beside it. Two refusals rather than guesses: a date-pinned cron whose shift crosses midnight (`0 4 1 1 *` → 31 Dec in Pacific) is unexpressible and stays UTC with a reason; and **DST is asymmetric** — Windows holds its local wall-clock across a transition, a Cronsole-native task does not, and the UI names that. `describeCron` and `/tasks/preview` both take the **UTC** form. |
| **Structured `exec` stays no-shell** (`{executable, args[]}`) | The P0 injection guarantee. A shell is opted into **explicitly** (`cmd.exe /c "…"`), never implicit. Implicit shell = arbitrary params become arbitrary code. |
| **`PlatformConnection.config` is AES-256-GCM encrypted** before Prisma write | At-rest guarantee. **Never log decrypted values.** |
| **Agent always initiates the WebSocket** | It lives on the user's machine behind their NAT. Inbound = a different (worse) product. |
| **Run commands are HMAC-signed per session** | Replay prevention. |
| **`(platform, externalId)` is unique** | `externalId` is the platform's native id (Windows task path, Claude routine id). |
| **Cronsole never writes under `\Microsoft\`** | `RegisterTaskDefinition` **silently overwrites** a same-named task in the same folder, and the agent runs **elevated** — so writing there could destroy a real Windows task with no error. Refused in the backend **and independently in the agent** (`TaskFolderPath`), because the agent holds the privilege and must not trust its caller. |
| **Cronsole creates exactly one folder unasked: its own `\Cronsole`** | The only one it also *prunes*. **Never create what you cannot remove** — deleting a Task Scheduler folder needs elevation, and trap [#28](../../docs/troubleshooting/README.md#28-a-restored-task-or-the-folder-it-landed-in-cant-be-deleted-access-is-denied) sharpened that further: the agent is **elevated**, so a folder it creates carries an administrator ACE and is a door only an **administrator** can close. A user's folder persisting is *correct* — it's theirs. **Two carve-outs, and they are the only two:** **restore** (`task:import`, 2026-07-28) and **task creation** (`createFolder` on `POST /api/tasks`, 2026-08-04). Both are **`false` by default**, both ride **inside the HMAC signature** (each widens what one command may create), and both **name every folder they created** in the response — including on failure, since a chain can be made and the write then fail. Neither may create under `\Microsoft\`. `\Cronsole` remains the only folder Cronsole ever *removes*. **There is deliberately no free-standing `create_folder`**: a folder must stay incidental to a task the caller asked for, or an agent feeling its way leaves `\AI-Tools`, `\ai_tools` and `\AITools` behind, permanently, at machine speed. |
| **`\Cronsole-Stack\` is not tracked in the dashboard** *(convention, not a guard — decided 2026-07-31)* | Those three tasks are Cronsole's **own launcher**: infrastructure that runs Cronsole, not work Cronsole runs. Tracking them puts the app in its own task list, where disabling `CronsoleAgent` from the dashboard takes the agent offline — which is also what stops the dashboard re-enabling it. It also keeps the `\Cronsole-Stack\` ↔ `\Cronsole\` split (prune-its-own-folder must never reach the launcher) true at the UI layer, not just in the agent. **Nothing enforces it**: Import lists `Cronsole-Stack` as an ordinary category, ticked under *Non-system*, so an unthinking "import everything" silently undoes it. Don't import it, and don't treat its absence as a bug. Status comes from `cronsole.ps1 status` and Task Scheduler. |
| **Every field the agent acts on is inside the signature** | Including the destination `folder` — an unsigned field on a signed command lets an on-path attacker redirect the write. |
| **Registry files are content-addressed (sha256 over exact bytes)** | Keep them **LF** (`.gitattributes`); **never hand-edit `registry/`**. A CRLF flip breaks integrity. |
| **`core` never reaches the DB** | `normalize.ts` whitelists Prisma fields. `core` is a distribution flag, registry-only. |
| **Prune-on-sync never touches `managed: false`** | Imported / saved-as-template rows are the user's. Only auto-synced (`managed: true`) rows outside core are pruned. Guarded against an empty core wiping the catalog. |
| **Platform logic stays in the connector layer** | Every integration implements `PlatformConnector`; no platform-specific logic escapes `backend/src/connectors/`. |
| **`ExecutionLog` records runs Cronsole *performed*, not runs that *happened*** | Rows come from exactly two places: `POST /api/tasks/:id/run` and `NativeScheduler`. **A Windows task firing on its own schedule writes nothing**, and a manual Windows run's `SUCCESS` means *"the agent started it"* — fire-and-forget, with `durationMs` timing the trigger, not the work. So a Windows task's real health lives in **Windows** (`lastTaskResult`, `lastRunTime`, `numberOfMissedRuns`, carried on the sync snapshot); only Cronsole-native tasks can be judged from `ExecutionLog`. Anything reading it as a complete run history is wrong at dashboard scale. **This decides each analytics view differently** (`services/runAnalytics.ts`): the failure trend reads it *labelled*; the duration trend reads **native rows only**; the idle report can't use it for Windows at all. |
| **A bulk operation reports per item, and its halt rule is not its failure rule** | At real scale partial success is the *normal* case, so every bulk verb returns five outcomes — `updated`, `unchanged` (already there: not a success to count, not an error to invent), `refused` (Cronsole declines *before* asking the platform, e.g. a `MISSING` task, or a native task that cannot be untracked), `failed`, `skipped` — never one number. **One definition, in `services/bulkOutcome.ts`**, shared by status / category / untrack, so a caller handling one report handles all of them. The **halt** rule is separate and belongs only to verbs that talk to the agent: `bulkStatus` **stops at the first agent-down signal** and marks the rest `skipped` with the reason, because each Windows task costs its full ~15s timeout and continuing turns one request into fifty copies of one error; a **per-task** refusal must *not* halt, since an ACL denial says nothing about the next task. Category and untrack never ask a platform, so they cannot halt — their `skipped` is structurally `0` and **stays in the response anyway**, because four zeros teach a caller something and four different response shapes teach it nothing. |
| **A category is a label; the folder is the machine** | `POST /api/tools/tasks/category` (and `PATCH /api/tasks/:id`) changes how the dashboard groups a task and **does not move it in Task Scheduler**. For a Windows task the two normally agree — the category is *derived* from the folder — so relabelling silently forks them. Not refused (it is a legitimate thing to want, and was always possible one task at a time), but **counted and named**: the response carries `detachedFromFolder` and the modal states it *before* the click, since a warning that arrives with the result arrives too late to change the decision. The folder verdict itself comes from `TaskService.extractCategory` and is passed *into* the planner — a second copy of a path-derived rule is trap #20a. |
| **Untrack is the bulk verb, because over-import is a bulk mistake** | `POST /api/tools/tasks/untrack` removes rows and records a `TaskExclusion` for each, in **one transaction** — a deleted row whose exclusion never landed comes back on the next sync, so the user does the work twice and trusts it less the second time. Affordable here precisely *because* there is no platform round-trip to hold the transaction open; `bulkStatus` cannot do the same, since each of its writes is only legitimate once the machine has confirmed it. It makes **no platform call**, so it works with the agent offline — which is exactly when someone is tidying up. The UI says "Remove from Cronsole", never "Remove". |
| **A destroy verb's blast radius is a property of the ROUTE it wraps, and a backup is a precondition or it is decoration** | Two rules, learned together on 2026-08-13. **(1)** `delete_task` wrapped `DELETE /api/tasks/:id` — the UI's route — so the one MCP verb that could not be undone had the *widest* reach on the surface, straight to a real Task Scheduler entry through the **elevated** agent. It now wraps **`DELETE /api/tasks/:id/native`**, refusing every platform but `TASKHUB_NATIVE` with a **400**. The property that buys is whole-surface: **no MCP tool can destroy an artifact on the machine** — Windows removal over MCP is `untrack_task`, and where delete *is* allowed the row **is** the task, so nothing is orphaned. Note this is **not `verbDeclaredUnsupported`**: that reports a boundary of the *platform*, and Windows deletes fine — this is a boundary of the *route*. **The check must live in the backend**, because a platform check inside `mcp-server/` is a *client-side* check the REST API still ignores; a guarantee that holds only for callers who used your wrapper is a convention, not a guarantee. **(2)** The route archives the definition + last 20 runs (`services/taskArchive.ts` → `DeletedTaskArchive`) **before** deleting, and **refuses the delete if the archive write fails**, leaving the task untouched — a backup that silently no-ops is *worse* than none, because the caller then proceeds believing the task is recoverable. So `archiveTaskBeforeDelete` **throws**, deliberately inverting `recordCapability`'s never-throw rule: an *observer* may not fail the verb it observes, but a **precondition that cannot fail is not one**. The archive carries **no relation to `Task` and no cascade** — it must outlive the row (the `TaskExclusion` shape, not `TaskFavorite`'s), and a cascade would drop the backup in the same transaction that made it necessary *while every other test still passed*. Read back at `GET /api/tools/task-archives[/:id]`; the bundle is built by the **same function** that serves `GET /api/tasks/:id/export`, so a restore path only ever learns one format. |
| **A status surface reports evidence, not preconditions** | The sharper, platform-level form of the rule below, and it cost a live defect. `getHealth` returned `HEALTHY` whenever a socket **object** existed and stamped `lastSync: new Date()` — so a wedged agent read as online and *"synced just now"* while every request against it timed out. **A socket existing is a precondition for health, not health**; Socket.IO's heartbeat is answered by the transport, not by the agent's command loop. And **a timestamp the observer generates can never be stale, which is exactly why it can never be true** — `new Date()` inside a health check is always a lie about something. Platform health is now the newest of `lastResponseAt` (any inbound event, hooked once via `socket.onAny` so no verb can forget) versus `lastFailureAt` (each request timeout, naming the verb): no socket → `OFFLINE`, timeout newest → `DEGRADED`, else `HEALTHY`. `lastSync` has **exactly one writer** — the column `POST /sync` writes — and `ConnectorHealth` has **no `lastSync` field at all**; liveness is reported separately as `lastContactAt`. **Connected is not synced.** *This row used to say `lastSync` was "a real inbound-event time, else the column", and that first clause was itself a bug*: `WindowsAgentConnector` filled it with `lastResponseAt`, so a **folder listing** made a 19-hour-old task list read as *"Synced 7m ago"* ([#42](../../docs/troubleshooting/README.md#42-the-dashboard-says-synced-7m-ago-over-a-task-list-from-yesterday)) — **#40 one level down, surviving #40's own fix**, because a *real* timestamp of the *wrong event* passes every honesty check an invented one fails. The sharpened tell: **ask what event writes a status field, and whether that is what the label names.** The same fabrication was in all three connectors, and fixing one was worthless: the dashboard chip takes the newest `lastSync` across *every* platform, so the never-syncing native connector alone would have pinned it. ([#40](../../docs/troubleshooting/README.md#40-the-sidebar-says-windows-is-online-and-synced-just-now-while-every-agent-request-times-out)) |
| **A capability is a property of the ROUTE, and a claim about *this install*** | The Platforms matrix (`services/platformCapabilities.ts`, `GET /api/tools/platforms`) says **verified** / **declared** / **unsupported**, and the middle one is the design: reachable but never observed to work is *not* yes. Two forbidden derivations. **Not `typeof connector.deleteTask === 'function'`** — that describes the code, not this machine (#40's shape), and it is *factually false* for **Cronsole-native**, whose delete, reschedule and export are handled inside `routes/tasks.ts` because the DB row **is** the task; a connector-derived matrix reports that platform as unable to do three things it does daily. **And not a boolean** — collapsing declared into verified is the spec-table lie the screen exists to prevent. Evidence lives in `PlatformCapability`, written by `recordCapability` at the routes; **that writer never throws** — an observer may not be able to fail the verb it observes. **And a third derivation is forbidden: "the interface mandates the method, therefore reachable."** True where the method reaches a platform, false where it is a hardcoded `{ success: false }` because no such API exists — a connector names those in **`unsupportedVerbs`**, which outranks every other rule. `declared` is a promise, `unsupported` is a boundary; Claude's `create` rendered `declared` invited waiting for evidence that can never arrive. |
| **A user-composed connection config gets its own validated route, and the secret is write-only** | Claude is the only platform whose credentials a user *types* — Anthropic mints a bearer token per routine and exposes no API to list them (`GET`/`POST`/`DELETE /api/tools/platforms/claude/routines`, `services/claudeRoutines.ts`, panel on the Platforms card). **No generic `PUT /platforms/:platform/connection`**: it would imply the others are configurable this way and would take an arbitrary blob into a field every connector trusts. The token is stored via `serializeConfig` and returned as **`hasToken`**, never the value — and there is deliberately **no reveal endpoint**, since claude.ai shows it once and cannot re-display it either. Re-adding an id **rotates** (generating revokes the predecessor, so the stored one is already dead); a pasted **fire URL is normalized** to its `trig_` id; shape mismatches **warn, never refuse** (experimental API); removing the **last** routine removes the connection so the card reads "Not connected" rather than permanent amber. |
| **A connector may be write-only or read-only, and must say which** | The Windows-shaped assumption — sync *and* mutate — is not the general case. **Claude Code exposes one endpoint** (`POST /v1/claude_code/routines/{trig_id}/fire`) whose token the docs describe as *"One routine only; no read access"*: `run` is real, `create`/`setStatus` are `unsupportedVerbs`, and `syncTasks` returns **what the user declared in config** — not a sync, and documented as not being one. The planned GitHub Actions / Vercel observers are the mirror image (read everything, change nothing). Both earn a connector over a quick link by one test: **does it do something a bookmark cannot?** Firing a routine does. ([#45](../../docs/troubleshooting/README.md#45-cronsole-cant-list-pause-or-create-claude-code-routines)) |
| **Evidence expires — a status field must be able to say it does not know** | The other half of the row above, and the half #40's fix did not have. Health is the newest `lastResponseAt` vs `lastFailureAt`, which had **no notion of an observation getting old**: one `task:folders` timeout at 21:05 left Windows reading *"connected but not responding"* for **ten and a half hours**, over an agent that answered a sync instantly when finally asked ([#48](../../docs/troubleshooting/README.md#48-windows-sits-at-degraded-for-hours-while-the-agent-is-perfectly-healthy)). #40 was a verdict from a **precondition**; this is a verdict from an **expired observation** — both first-hand, neither invented, and neither able to say how old its evidence was. `HealthState.UNKNOWN` ("Not checked") + `UNRESPONSIVE_EVIDENCE_TTL_MS` (15 min). The rule that makes the TTL non-arbitrary: **evidence of a connection renews itself and evidence of a failure does not** — the transport re-proves the socket continuously; a timeout happens once and nothing after it asked. So a socket may stand forever and a timeout must age out, and an agent someone is actively using stays `DEGRADED` because each attempt renews it. **UNKNOWN is the absence of a verdict, not a fourth severity**: neutral colours (amber makes missing information look actionable), it also covers *never exercised* (Claude's four no-evidence branches; `@default(UNKNOWN)` so no connection is born Online), and it must rank **above healthy** in any summary — *"All 3 platforms online"* over a platform nothing has heard from since yesterday is worse than the amber it replaced. **No probe**: `getHealth` runs on a 45s poll, so probing means a synthetic agent request per open tab; Sync is the user's probe. |
| **A health check may not have a side effect** | Where the *only* endpoint mutates, there is no probe: for Claude, "check whether this works" and "run the user's nightly job" are the same request, so a probing `getHealth` burns their daily run cap on every poll. Health is then read back from the run evidence already in `PlatformCapability` — never invented, and never from a precondition (it returned `HEALTHY` whenever config was non-empty, which is #40 one connector over). Corollary in the enum, **closed 2026-08-13**: "configured, never exercised" used to borrow `DEGRADED` + a reason, because `HealthState` had no `UNKNOWN`. It has one now — see the row above — and with it went the `@default(HEALTHY)` and the hardcoded `healthState: 'HEALTHY'` that made `/api/tasks/health` stamp Windows healthy at auto-init before the agent had ever spoken. |
| **A status readout may not change its own geometry** | The dashboard health strip is one fixed-height scrolling line. As `flex-wrap` it went one row to two whenever a segment appeared, moving the whole dashboard down ~22px on a 45-second poll. Generalizes to the visual suite: **masking hides colour, not geometry** — a live-data element whose size tracks its content de-stabilizes everything laid out beside it, mask or no mask ([#43](../../docs/troubleshooting/README.md#43-a-visual-regression-baseline-fails-on-one-pixel-or-on-a-layout-that-moved-by-itself)). |
| **A clickable `<div>` is not a control** | It is unreachable by keyboard and has no accessible name, so the dashboard's primary action was mouse-only. The fix is not a `tabIndex` — the task card **contains** the row-action buttons, and a button may not nest in a button, so the *title* became the real control (*"Open details for &lt;task&gt;"*). Same pass: all 8 modal close buttons were unnamed icons. |
| **Absence of evidence is `unknown`, never `ok`** | The health scorer's core rule, and it generalizes. A field the agent has never reported is *absent*, not zero — an un-republished agent omits `lastTaskResult` entirely, and reading that as "never ran" would flag every Windows task at once. Keep "we were never told" distinct from "we were told there is nothing", and never let silence render as health. **It has to survive into the UI:** the dashboard's *Failures* chip renders `–`, not `0`, until the health scan lands — with no tiers every task is `unknown`, so the list is empty, and an empty list asserts *"nothing is failing"*. Related: **never mix populations in one row of numbers** — the Task health card took three tiers from the personal list and `Healthy` from the whole machine, printing `12 · 25 · 1 · 218` under "across 352 tasks" (sums to 256; fixed 2026-07-31). |
| **Colour is a semantic role token, never a raw Tailwind palette utility** | `bg-amber-500` / `text-red-400` are banned in `frontend/src` (zero remain). Use `success` · `warning` · `danger` · `isolate` · `info` · `system` · `neutral-text`, plus `native` / `claude` / `chatgpt` identity, all in `index.css`. Each is a **pair**: `--x` = accent for fills/borders (`bg-warning/10`), `--x-text` = the role as text on the page background. Separate because **the text version inverts between themes and the accent does not** — a raw literal cannot do both, which is why every status role failed WCAG AA in light (1.67–2.77 vs white; now 5.05–8.65, dark unchanged at 7.15–11.70). Traps: **`-text` ≠ `-foreground`** (`-foreground` is text *on* a solid fill); and **a shared hue is not a shared role** — merging by appearance would have folded ChatGPT's brand emerald into `success`, Claude's purple into the system lens, and the isolating-lens rose into failure red. Platform identity lives in `platform.ts`. `--raised` is the neutral step above `surface`. |
| **Friction scales with the blast radius — and a scope is what lets it** | A confirmation identical at 3 tasks and at 254 never hardens, so habit built on small batches carries into a machine-wide one. Past `TYPE_TO_CONFIRM_THRESHOLD` (25) the dialog requires **typing the count**, and it always **names the scope in words** — `254 selected` cannot be checked by a reader; *"every tracked task of yours"* can. Hence the scope-first Mass Actions console (`utils/massActions.ts`, `components/tools/MassActionsTool.tsx`). **Dashboard row selection was removed entirely (2026-08-12)** — bulk work is only the Mass Actions console, which is **action-first** (pick a verb, then its scope). Selection could not survive into a confirmation as anything checkable, and `Select all 269` built a batch every bulk button 400'd on. The safe-path objection failed on inspection: **Remove from Cronsole sits beside Delete from Windows in the task modal, per task**. Corollary that holds: **moving a control to another tab is not safety** — obscurity wears off; the typed confirmation carries it. The console **chunks** at `MAX_TASKS_PER_BULK` (100). Chunk, don't raise the ceiling: it is a correctness bound (each Windows task can cost its full ~15s agent timeout), and batching buys progress plus a halt point. A halt names every remaining task `skipped` rather than letting it vanish. |
| **A source is finer than a platform** | *Platform* = what Cronsole talks to (one connector, one capability row). *Source* = what the user navigates by. They diverged when Cronsole-native gained a second job type: an HTTP job and a script are the same platform and different things. Key is `PLATFORM` or `PLATFORM:SUBTYPE`, derived **server-side** (`services/taskSource.ts`) and sent per task like `isSystem` — deciding it reads `metadata.job.jobType`, and a browser copy of that judgement is #20a's shape. **The Platforms tab does not split** (same connector, identical capabilities). **Matching is prefix-aware** (`sourceMatches`), which is what let the split ship without emptying every stored `defaultPlatform`. **The selected source stays listed even when no task derives it**, or a pre-split link filters the list with the whole bar unlit — the lit-chip problem inverted. |
| **Source is the outer lens, and a view does not own it** | *Where a task comes from* is the dashboard's first-level axis (`SourceBar.tsx`), above the saved views. `filtersEqual` **ignores `platform`**, so picking a source leaves the view chip lit instead of dropping to *Custom* — legal only because both are on screen, since the rule being bent is about **hidden** constraints. Obligations that follow: source rides **alongside** the view id in the URL (a matched view returns early and would swallow it); saved views **do not store** one (`viewFiltersFrom` strips it — `matchView` never reads it, so it would be dead state); the Filters badge **does not count** it (a count may only describe what its own drawer can clear); and **view counts are taken inside the selected source**, or `My jobs 88` sits above one row. **And an outer lens may not vanish because an inner filter narrowed the list** — built from the faceted population the bar disappeared on any single-source view, taking the only control that could switch away. Existence comes from the whole list; only the count is faceted, which is why a source may read `0`. |
| **A native `EXEC` job inherits no environment, and says where it runs** | Cronsole-native runs programs as of 2026-08-12 (`{executable, args[]}`, the same no-shell `StructuredAction` the Windows path uses). **`childEnv()` passes an allowlist, never `process.env`** — this backend holds `JWT_SECRET` and the AES key encrypting every `PlatformConnection.config`, so an inheriting script could read out the key that protects every stored credential, through the same UI that created the task. Mutation-tested. **And the job states its execution host**: native runs wherever the *backend* runs, which is inside the container on a Dockerized install — the same spec then executes against a filesystem that is not the user's and fails as "executable not found" for a file they can see. `services/runtimeContext.ts` detects it at boot; the New Task modal says which. *Corollary:* a script that must run **as the user** or survive Cronsole being down belongs on the **agent**, not on native. |
| **A count beside a filter control is a promise about what clicking it reveals** | So it counts the population that control **governs** — every task passing every *other* lens — not the dashboard total and not the filtered list. Use `applyTaskFiltersExcept(tasks, filters, dimension, opts)` (`utils/taskFilters.ts`); `applyTaskFilters` delegates to it, so a dimension cannot live in one and not the other. Counting over the raw list is what printed **`Showing All 269` above the two rows** the Favorites view was showing (fixed 2026-08-12). Two corollaries: the hidden count is **derived** (`governed.length - filtered.length`), never counted by its own route that can then disagree with the list above it; and a control **labels the dimension it owns** — `All statuses`, not `Showing All`, since status is one lens of eight and the rest are still in force. |
| **In-app help summarises a doc, links to it, and the link is checked** | Every `?` (`components/HelpButton.tsx`) opens one topic from `data/help.ts`; **`HelpTopic.doc` is required**, because a topic with nowhere to point explains something undocumented and the fix is a doc — not a popover that becomes the only place a rule is written down. **The links are the worst kind of mirror surface**: a renamed heading does not fail, GitHub just serves the page scrolled to the top, so a control promising *"Removing a task"* silently delivers the table of contents. `frontend/src/data/__tests__/docsLinks.test.ts` resolves each URL to a real file + heading and **fails on a repo path it does not import** rather than skipping it. Two ways it can pass while proving nothing, both real: splitting CRLF markdown on `\n` leaves a `\r` that `.` won't match → **zero** anchors; and collapsing whitespace runs in the slug is wrong, since GitHub doesn't (an em dash removed leaves two spaces → two hyphens). **Hub and topics are one component** — a `?` is findable only if you're already at the control, a hub only if it reaches what those buttons say. Source help resolves per source (`sourceTopicId`), degrading key → platform → overview like `sourceLabel`. Docs read via Vite `?raw`, and `server.fs.allow` is widened in **`vitest.config.ts` only** so the dev server keeps its sandbox. |
| **A catalog with nothing for a source is a source the product does not really have** | Cronsole-native was a first-class source on the dashboard, in the matrix and over MCP for six weeks while **zero of the 55 templates targeted it** — so the Templates tab had nothing for a user with no agent. Fixed 2026-08-13 with a native family (6) and a Claude-routine family (5), **and the connector path that applies them, in the same change**: `CronsoleNativeConnector.createTask` refused every non-URL command, so a native script template would have applied to a refusal. Rules that came with it: **one definition of what a native task runs** — `buildNativeJob` now lives in `services/nativeJob.ts`, shared by `POST /api/tasks/native`, `PATCH /:id/job` and the connector, with `nativeJobFromCommand` deciding **URL → HTTP, anything else → EXEC** (safe in the only direction that matters: a URL is not a runnable executable); and **`POST /api/tasks` must not upsert a native row it did not write**, since the connector already wrote `metadata.job` and the generic upsert would replace it with the `{schedule, command}` shape, leaving a task the executor refuses to run after a create that reported success. |
| **What Cronsole can create *here* is a server verdict, and the browser renders it** | The Templates tab held `CREATABLE_PLATFORMS` as a literal until 2026-08-13 — a browser copy of what `GET /api/tools/platforms` already computes per user (trap #20a's shape), and wrong in **both** directions within two days. It cannot be a constant at all: for Claude the answer depends on whether a Claude Code session is readable on the backend's machine. `usePlatformCreatability()` gives **three** answers — `yes` (verified *or* declared: refusing declared waits for evidence only applying can produce), `no`, and `unknown` while the matrix is in flight. **`unknown` asserts nothing** — the target stays selectable and only **Apply** is gated, because an optimistic selection is recoverable and an optimistic submit is a request the platform may refuse. |
| **Editing what a task runs is two routes, not one** | `PATCH /:id/actions` asks the elevated **agent** to rewrite a task on the machine and records nothing until the platform confirms. `PATCH /:id/job` rewrites a **Cronsole-native** job spec, where the DB row *is* the task — the write is the change, nothing can refuse it, and it works with the agent offline. One handler would need half its paths to wait for a round trip the other half does not have. Native rules: it **replaces the job, never merges** (the two job types share no fields, so a merge strands `url` inside an EXEC job — the UI names what a type switch discards *before* the click); it reuses **`buildNativeJob` + `validateJob` from the create route**, since a second definition is how an edit yields a spec creation would have refused; and `'updateAction'` sits in **`NATIVE_ROUTE_HANDLED`**, or the matrix calls native unable to change what it runs. |
| **`name` and `category` are Cronsole labels; sync overwrites neither** | `upsertTasks` sets both on `create` and only platform facts on `update` (status, metadata, schedule, `nextRunTime`), so `PATCH /api/tasks/:id` can edit them and the edit survives. `name` joined `category` here on 2026-08-12; until then sync wrote it back every pass, which is the whole reason renaming was never offered. **The line was structurally a no-op** — no platform can supply a *new* name for an *existing* row: a Windows task's name is the last segment of its path and the path **is** `externalId`, so renaming on the machine yields a different task (old path `MISSING`, new path imported); measured first, 354 Windows tasks, **zero** whose name differed from their path leaf. Two obligations: a rename is **DB-only**, so the UI keeps the real `externalId` on screen and **says so once the two diverge** (or someone searches Task Scheduler for a name that was never there); and it **cannot collide**, since the duplicate guard exists for *create*, where the name becomes the path. |
| **Where the platform's state is the user's own declaration, "untrack" cannot be true** | `TaskExclusion` assumes the Windows shape — the task is on the machine, sync enumerates the machine, Cronsole remembers *"don't re-import this"*. `CLAUDE_CODE` inverts it: no list API exists, so `syncTasks` returns the routines declared in `PlatformConnection.config` and **the registry is the platform**. An exclusion there fences the config off from itself while the declaration sits untouched, and importing the category clears exclusions **by design** — so the task returns and the exclusion table reads *empty*, as if untrack never ran. Untrack now **400s for `CLAUDE_CODE`** (as it already did for `TASKHUB_NATIVE`), `DELETE …/claude/routines/:id` **removes the tracked tasks with the declaration** and writes **no** exclusion, and the modal offers *Disconnect routine*. **Why refuse instead of making untrack remove the routine too:** that button silently spends an API token claude.ai shows **once** — **a control may not spend something its label does not mention.** ([#47](../../docs/troubleshooting/README.md#47-a-claude-task-keeps-coming-back-after-remove-from-cronsole)) |
| **A judgement has one definition, and it lives on the server** | The dashboard's *Failures* view filters on the tier from `GET /api/tools/task-health`. Do **not** reach for `lastRunStatus === 'FAILURE'`: for a Windows task that value records the agent *accepting a start*, not the job's outcome, and the correct reasoning (Windows' `lastTaskResult`, minus Task Scheduler's informational codes like `267009`/`267014`) already exists in `services/taskHealth.ts`. A second copy in the browser is the drift that took a folder out of every sync (trap #20a). Same rule as `isSystem`: **the server sends a verdict, the browser renders it.** |
| **Dashboard filter state is one `TaskFilters` object, held in the URL** | `frontend/src/utils/taskFilters.ts` + `savedViews.ts`. A new filter is a *field on that object*, never a seventh `useState` beside it — that is how the fifth filter gets applied to the list but not the counts next to it. A view is a **bookmarkable URL** (history written with `replace`, not `push` — filters are a state of the page, not a sequence of pages); a matched view **always** writes its id, since a bare URL already means "this user's saved defaults" and two states cannot share one encoding; and the **built-in views are code, not data**, so a later fix to what "Failures" means is not frozen into each user's `localStorage`. Tweaking any filter must fall back to "Custom" — a lit chip over a list it no longer describes is `Active Only` hiding 110 rows all over again. |
| **A favorite is about a tracked row; an exclusion is about a removed one** | `TaskFavorite` is keyed on **`taskId` and cascades**. `TaskExclusion` is keyed on **`(platform, externalId)`** precisely *because* it must **outlive** the row — without that, the next sync re-imports what the user untracked. Reversing either is a real bug: a star that survived a delete comes back attached to nothing, or to a re-imported task nobody starred. Both are per-user **joins**, never columns on the entity — a column makes one tenant's star everyone's (same reason as `TemplateFavorite`). The **Favorites view sets `status: 'any'` + `system: 'include'` on purpose**: a star is an explicit per-task choice, so no *default* lens may overrule it, or the star means "shown, conditions apply". |
| **A filter the app applied to itself has to announce itself in the page** | The rule, still standing: a constraint the user did **not** choose must be named in the page, not in a tooltip — a lit chip is enough for a view you clicked, not for one that arrived on its own. **The case that produced it is gone**: the dashboard opened on Favorites from 2026-08-11 until 2026-08-12 and now opens on **All** (`openingFilters(defaults)`), so nothing is withheld and the banner that named it was deleted with it. Keep the rule; it applies to the next self-applied default, not to this one. |
| **Dark theme is the default**, light is the toggle | Not an opt-in. |
| **There is exactly one account-creation path: `POST /api/auth/setup`** | First run only; 409 once an owner exists. The generic `POST /register` was **deleted 2026-07-31** — an unauthenticated account-creation endpoint on a service that runs commands on the user's machine. **Do not re-add one for a test's convenience**; that is precisely how it survived. An integration test pins the 404. |
| **One origin list gates both REST CORS and the Socket.IO handshake** | `backend/src/config/origins.ts`, read by `app.ts` and `index.ts`. They were separate — a bare `app.use(cors())` beside a restricted socket — and two mechanisms answering one question is how one quietly stops matching the other. A request with **no `Origin`** is always allowed (non-browser callers; auth is their gate), and an empty list stays permissive **but warns at boot**. |

## ⚠️ The traps

These have each burned real hours. **Check these before debugging your own code.**

| Trap | The tell | Fix |
|:---|:---|:---|
| **A status field is first-hand, correctly stale — and still the wrong event** | The header says *"Synced 7m ago"* over tasks whose cards read `Last updated` yesterday, and `/api/tools/platforms` and `/api/tasks/health` return **different** `lastSync` for the same platform. | `getHealth` reported the agent's last inbound event of *any* kind (`lastResponseAt`, hooked via `socket.onAny`) as `lastSync` — the 7-minute stamp was a folder listing. Fixed by deleting `ConnectorHealth.lastSync`; connectors report `lastContactAt`. **Ask what event writes a status field, and whether that is what the label names** ([#42](../../docs/troubleshooting/README.md#42-the-dashboard-says-synced-7m-ago-over-a-task-list-from-yesterday)). |
| **`prisma generate` fails `EPERM`, and killing "the backend" does not help** | `EPERM: operation not permitted, rename '…query_engine-windows.dll.node.tmp…'` right after `migrate deploy` succeeded — and it *still* fails after you stop whatever holds port 3000. | The running backend holds the query engine DLL ([#26](../../docs/troubleshooting/README.md#26-prisma-generate-fails-with-eperm-operation-not-permitted-rename--query_engine-windowsdllnode)) — but on `npm run dev` that is **`tsx watch`, two processes**. Port 3000 is the **child**; killing it leaves the watcher, which respawns and re-locks. Match `*tsx*watch*` by command line instead. The watcher also restarts on every source edit and the child PID rotates, so retrying never wins. Afterwards, check *what* restarted it: with `\Cronsole-Stack\` installed the self-heal task may beat you to it, so your `npm run dev` dies `EADDRINUSE` while `/api/health` returns 200 ([#26a](../../docs/troubleshooting/README.md#26a-and-on-the-npm-run-dev-stack-the-fix-above-kills-the-wrong-process)). |
| **A screenshot baseline fails on 1 pixel — or on a layout that moved by itself** | `1 pixels (ratio 0.01) are different` with nothing changed; or the page shifted ~22px between identical runs. | Three causes, none of them flake: `maxDiffPixels` defaults to **0** and GPU antialiasing is not deterministic (set 40 — far above the noise, far below one character); **masking hides colour, not geometry**; and a `flex-wrap` status line changes its own **height**, which is a real defect. Don't pixel-baseline a surface that is mostly live evidence — assert it structurally ([#43](../../docs/troubleshooting/README.md#43-a-visual-regression-baseline-fails-on-one-pixel-or-on-a-layout-that-moved-by-itself)). |
| **An `aria-label` silently breaks an existing E2E locator** | A Playwright spec times out `waiting for getByRole('button', { name: /^Import$/ })` on a button that is plainly on screen. | Adding `aria-label="Import tasks"` **replaces** the accessible name; `getByRole` matches on that, not the visible text. Naming icon-only controls is right — but grep `tests/e2e` for the old name in the same change. |
| **An MCP tool 400s on every call while `npm test` is green** | `Unsupported jobType: undefined` (or any shape rejection) from a tool whose suite passes — including a test *named* after the agreement it is not checking. | The MCP suite **stubs the HTTP client**, so every assertion is about what the wrapper *sends*, never whether the API *accepts* it. A test can pin a payload the server rejects and pass forever — it does not miss the bug, it **freezes** it. `create_native_task` had never worked since it shipped. **Drive a wrapped route by hand after touching it**; one `curl` with the tool's exact payload is the whole check ([#44](../../docs/troubleshooting/README.md#44-an-mcp-tool-400s-on-every-call-and-the-whole-suite-is-green)). |
| **A documentation search recorded as a fact about the platform** | Claude routines "don't sync", Enable/disable is greyed out, `create` is `unsupported` — all traced to *"Anthropic exposes exactly one routines endpoint"*, written into the architecture as a boundary. It was true of the **documented** API and false of the product: Claude Code creates and lists routines through `/v1/code/triggers` the whole time. | **A doc search is evidence about docs; a capability claim needs evidence about the platform.** Drive the verb, or find the vendor's own client doing it, before calling it impossible — "unsupported" is the most expensive cell in the matrix to get wrong, because nobody re-checks a boundary. The `400 = paused routine` half of the original finding survived and is still right. ([#50](../../docs/troubleshooting/README.md#50-two-claude-routines-apis-and-the-documented-one-is-the-smaller-one), superseding [#45](../../docs/troubleshooting/README.md#45-cronsole-cant-list-pause-or-create-claude-code-routines).) |
| **A capability test that depends on the developer's machine** | `ClaudeConnector.unsupportedVerbs` is a **getter** — its answer changes with whether a Claude Code session is readable. An unmocked test therefore passes locally and fails in CI, or worse, the reverse. | Mock `getClaudeCredential` and state which mode each case is in. The same applies to anything asking the capability matrix about Claude. |
| **A hand-written partial enum in a test mock lies quietly** | A unit test asserts the wrong branch while the same code returns the right answer against the live server. | `vi.mock('@prisma/client')` supplied `PlatformType: { WINDOWS_TASK_SCHEDULER: … }` only, so `PlatformType.CLAUDE_CODE` was `undefined`, every comparison against it was false, and the else-branch was asserted as correct. A partial copy of a **generated** enum cannot fail loudly — it just silently omits members. Use `vi.mock('@prisma/client', async importActual => ({ ...await importActual(), PrismaClient: FakeClient }))`: the enums are plain string constants and need no database. Same family as [#44](../../docs/troubleshooting/README.md#44-an-mcp-tool-400s-on-every-call-and-the-whole-suite-is-green) — a stub asserting agreement it never checked. |
| **A "harmless" default payload displaces the real one** | A routine built for alert triage receives `Triggered from Cronsole` where the alert should be. | `runTask` sent `text: 'Triggered from Cronsole'` on every fire. That field arrives inside the routine's `<routine-fire-payload>` block — inert for most routines, and for the ones whose prompt *reads* that block it is the entire input. The body was optional all along. **A filler value in a pass-through field is not neutral; it is a value.** |
| **Every local suite is green and CI is red** | `npm test` passes in all four packages; the push goes red on `@typescript-eslint/no-explicit-any`, or on one integration assertion, six commits running. | **`npm test` is not the CI gate.** Two steps have no equivalent it runs: **`cd frontend && npm run lint`** (only the frontend is linted, and `no-explicit-any` is an *error* — `catch (e: any)` and `(api.post as any)` are the recurring shapes; use `utils/errorMessage.ts` and `vi.mocked(fn)`) and **`cd backend && npm run test:integration`** (separate vitest config + real Postgres). Note the asymmetry that bites: **a status-code change is invisible to unit tests and loud in integration tests** ([#46](../../docs/troubleshooting/README.md#46-every-local-suite-passes-and-ci-is-red--npm-test-is-not-the-ci-gate)). |
| **A removed task keeps coming back, and the exclusion table is empty** | "Remove from Cronsole" reports success on a **Claude** task; minutes later the row is back with a new `createdAt`, and `TaskExclusion` has **zero** rows — which reads as "untrack never ran". | It ran, and its exclusion was then legitimately deleted. `ClaudeConnector.syncTasks` returns the routines declared in `PlatformConnection.config`, so the exclusion fenced the user's own config while the declaration stayed — and importing the Claude category clears exclusions *by design*. **Disconnect the routine**, which removes the declaration and its tasks together; untrack now refuses this platform outright ([#47](../../docs/troubleshooting/README.md#47-a-claude-task-keeps-coming-back-after-remove-from-cronsole)). |
| **Backend edits don't hot-reload in Docker** | Offline suites pass, but a live request disagrees with the source. A new route 404s. | `docker restart taskhub-backend-1`. Windows→Linux bind mounts don't propagate inotify, so `tsx watch` never fires. |
| **The .NET agent never hot-reloads** | New agent command 502s "Agent … timeout" after ~15s. Route **exists** (bad id → your handler's error, not "Cannot GET"), and only agent-backed paths hang — DB-only paths work. | Republish it from an **Administrator** prompt (it runs elevated; the exe is locked). |
| **Transient test agent strands the real one** | Windows shows `OFFLINE` forever after you stop a second/dogfood agent, though the real agent is still running. | `docker compose restart backend`. One agent socket per user; the real agent only re-registers on reconnect. |

## Working rules

1. **Start from `docs/ROADMAP.md`.** It's the plan of record. A material decision updates it **first**, then you implement.
2. **Check `docs/troubleshooting/README.md` before debugging** any setup/runtime failure. Most "impossible" behavior is a known trap above.
3. **`context7` before writing** against React, Prisma, Express, Socket.io, Tailwind, .NET, or WiX.
4. **Templates are content, not code.** Never inline them in `seed.ts`. Edit `bundled.ts` → `npm run registry:build` → publish.
5. **Never hand-edit `registry/`.** It's generated and content-addressed. The drift test will fail you.
5a. **Same for the Connect Pack.** Edit the markdown in `backend/src/tools/connect-pack/`, then `npm run connectpack:build` — never `connectPackBundled.ts` directly. It's bundled rather than read from disk because **`tsc` emits only `.js`**, so loose `.md` under `src/` never reaches `dist/`: a filesystem read would work under `tsx` in dev and 404 in production. A drift test fails if the bundle and the markdown disagree.
6. **A material change ships with its test.** A bug fix ships with a test that failed before it.
7. **Four things run stale**: the Dockerized backend, the published agent, `mcp-server/dist/`, and — the newest and quietest — **the container's generated Prisma client** (`node_modules` is a shadowed volume, so a host `prisma generate` never reaches it; the DB and the client then disagree, and a missing enum member becomes a silent partial write, [#22](../../docs/troubleshooting/README.md#22-deleted-a-windows-task-synced-and-cronsole-still-shows-it--while-reporting-missing-n)). When live behavior contradicts source, suspect these before your logic.
8. **Prefer the honest refusal** over the graceful lie. See "The one thing to understand."
9. **The MCP server and this skill are mirror surfaces — update them in the same change.** See below.
9a. **So are the two published surfaces, and they are the only ones a stranger reads.** A catalog
    change needs `npm run registry:build` **and** `pwsh scripts/publish-registry.ps1` — installs
    fetch the hosted registry, not this repo, so an unpublished fix is still broken for every user
    and **nothing fails to tell you**. A change to what the gallery claims Cronsole can do needs
    **both** publish scripts: one page, two hosts. Never keep manual work in the two publish clones
    (`Repos/Tools/cronsole-registry`, `Repos/Tools/cronsole-site`) — each script `git reset --hard`
    them first.
10. **Commits**: conventional prefix, imperative subject (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`).
11. **Never commit** `.env*`, `node_modules/`, `dist/`, `bin/`, `obj/`, `*.msi`.

## Two skills, two audiences — don't merge them

There are **two** Cronsole skills, and confusing them ships the wrong document to the wrong reader:

| | This skill (`skills/cronsole/`) | The Connect Pack (`backend/src/tools/connect-pack/`) |
|:---|:---|:---|
| **Reader** | Someone working **on** the Cronsole codebase | An end user's AI tool **using** a running Cronsole |
| **Contains** | Architecture, catalog internals, the agent protocol, repo traps, test layers | The tool surface, the invariants, schedule traps, how to verify |
| **Ships via** | The repo, through a per-machine junction | A download in the dashboard's **Tools** tab |
| **May reference** | `catalogSync`, `normalize.ts`, `bundled.ts`, repo-relative links | **None of those** — an audience test fails the build if they leak in |

Distributing *this* skill to end users would hand them registry-publishing internals instead of
usage instructions. When you add a capability, ask which reader needs it — often both, in
different words. The pack is **version-stamped** because a copy on someone else's machine is a
mirror surface you can never update: it can't be kept current, so it must be able to say how old
it is.

## Keeping the mirror surfaces in sync

`mcp-server/` and this skill both **describe** Cronsole rather than implement it, so neither
breaks loudly when it drifts — the tests stay green, and the drift surfaces later as an agent
confidently doing the wrong thing. That's "the confident lie" aimed at your future self.
**They don't get a follow-up pass; they ship in the same change.**

**Ask on every change: "would an agent reading only this skill now be wrong?"** If yes, the
change isn't finished. Same question for the wrapper: a route whose shape moved leaves
`mcp-server/` lying about the API it wraps.

Two asymmetries worth holding onto:

- **The repo wins.** When this skill and a doc disagree, the doc is right — fix the skill.
- **`mcp-server/` holds no logic.** If syncing it tempts you to add behavior there, that
  behavior belongs in a backend route. A wrapper that grows logic stops being a wrapper, and
  the guarantees quietly fork.
