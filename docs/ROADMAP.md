- **Agent-auth hardening follow-ups** (closes the three residuals from the 2026-07-09 WebSocket-auth review): **(1) the `task:create` trigger is now signed.** The HMAC message gained a canonical trigger field (`canonicalizeTrigger` in `utils/scheduler-conversion.ts` / `AgentAuthenticator.CanonicalizeTrigger` in C# — a fixed-order pipe-joined form, null → `"none"`), so an on-path attacker on a plaintext connection can't rewrite a task's *schedule* in flight any more than its command. The agent parses the trigger *before* verifying and includes its canonical form in the checked message; the shared cross-language golden vector gained a null-trigger and a Weekly-trigger create case. **(2) Per-command replay guard.** The agent now rejects a `(ts, sig)` it has already accepted within the freshness window (bounded, self-pruning cache mirroring the server's handshake nonce cache), so a captured command frame can't be replayed on a plaintext link. **(3) Session-key reconnect overlap.** The agent kept a single mutable session key, so a command signed under the old connection that was still in flight when the socket rekeyed was false-rejected; it now keeps the current key (non-expiring) plus any superseded key for a `MaxSkew` grace window and verifies against either. A **latent bug caught in live verification**: the first cut expired *every* key after 120s, which silently broke all commands on any connection older than two minutes (the unit tests all verified within the window, so they passed) — fixed so the current key never expires. `emitSignedCommand`'s `extra` param was dropped (trigger is now a first-class signed field). **Breaking** — the create signature changed, so agent + backend must deploy together; the agent was republished for verification. Verified live end-to-end: rebuilt both sides, created a Windows task with a real Daily trigger (registered with the correct trigger + args), and ran a signed `task:run` **>120s after the handshake** to confirm the long-lived-key fix. Backend 121 tests (+3 trigger-canonical), agent 56 tests (+10: trigger canonical, replay, rekey-overlap, tampered-trigger-rejected). *(2026-07-10)*
- **Server-side per-token template substitution** (P1 command-handling follow-up — closes the last structured-command residual): the Apply modal used to substitute `{{placeholders}}` client-side and send the finished command string, which the backend then tokenized — so a parameter value with an unbalanced quote could split into extra literal args (harmless without a shell, but not what the author wrote). Now the client sends **raw parameter values** and the backend owns substitution (`backend/src/utils/templateCommand.ts`): the template is tokenized *first* (a new quote-tracking `parseCommandTokens` in `commandParser.ts`), then values substitute per-token — a quoted/composite placeholder (`-File "{{scriptPath}}"`, `--flag={{v}}`) is always exactly **one argument** regardless of its contents, while a bare placeholder token (`{{args}}`) keeps its intended multi-arg semantics, contained to that position. Raw params are validated server-side against the template's declared parameter definitions (required non-blank, `select` ∈ options, undeclared keys / non-string values rejected — each a specific 400). The resolved `{executable, args[]}` rides `CreateTaskOptions.action` to the Windows connector (no re-tokenization; still covered by the task:create HMAC), non-argv platforms (native HTTP jobs) get whole-string substitution, and the legacy pre-substituted `command` body field still works (deprecated). No agent change needed. **Verified end-to-end live**: applied the PowerShell Script starter from the browser with a spaced path → registered as one quoted `-File` arg; probed with `scriptPath = C:\nonexistent\x.ps1" & calc.exe` → registered as a **single backslash-escaped argument** to powershell.exe (no second process possible); API probes confirmed all four 400 paths. Noted while verifying (existing behavior, already backlogged in the P2 Apply-modal task-name item): re-applying a template with the same name silently overwrites the existing Windows task. Backend 116 tests (+23: `templateCommand` suite), frontend 45. *(2026-07-10)*
- **Structured command handling — no more `cmd.exe /c` shell wrap** (fourth P0 blocker done → **P0 security complete**): the agent registered every created task as `new ExecAction("cmd.exe", "/c " + command, null)` — the whole command string ran through a shell, so a template parameter substituted into it (e.g. a `{{scriptPath}}` of `x.ps1 & calc.exe`) was interpreted by cmd = command injection / RCE on the user's machine. Now the backend structures the resolved command into `{ executable, args[] }` server-side (`utils/commandParser.ts`, a quote-aware tokenizer) and the agent registers a **direct ExecAction** — no shell — quoting each argument by Windows `CommandLineToArgvW` rules (`ArgumentQuoting.cs`). Because no shell parses the line, a malicious parameter can at worst become a malformed argument to the *intended* executable; it can never launch a second process. The structured action is **covered by the task:create HMAC signature**: the signed message gained an action-canonical field (executable + args joined by 0x1F), computed identically on both sides and pinned by the shared cross-language golden vector (backend Vitest + agent xUnit both assert the new `createSig`). The `ITaskScheduler.CreateTask` contract now takes an `AgentExecAction` instead of a command string; commands that genuinely need shell features name the shell explicitly (two Tier-B seed patterns updated: `pg_dump … > backup.sql` and `del /q %temp%\\*` now use `cmd.exe /c "…"`). **Breaking** — agent + backend must be deployed together (the create signature changed). Verified: backend 93 tests (+10: `commandParser` + updated vectors), agent 46 tests (+7: `ArgumentQuoting` + updated create/vector tests). Residual (P1): the backend tokenizes the *client-substituted* command, so a parameter with an unbalanced quote could split into extra literal args (harmless without a shell) — robust per-parameter server-side substitution from raw params would remove even that. *(2026-07-09)*
- **Multi-tenancy route scoping + JWT fail-fast + dev-JWT rotation** (third P0 blocker done): the task API previously ran as a single hardcoded `cli_user_placeholder` and, worse, its by-id routes looked tasks up by `id` alone — so any authenticated caller could **list every user's tasks** (`GET /tasks` had no `where`), and read/patch/delete/**run** *anyone's* task by guessing an id (IDOR → the run path is remote command execution on another user's agent). Every task route now derives `userId` from the verified JWT (`req.user.id`, via the already-mounted `authenticateToken`), and all lookups are owner-scoped: `GET /tasks` filters `where:{userId}`; `PATCH`/`DELETE`/`POST /:id/run` use `findFirst({id, userId})` (404 on a miss); `GET /:id/executions` confirms task ownership before returning logs; create/native/health/sync/discover and the template **apply** route all attribute to the token user. Backend now **fails fast on a missing/weak `JWT_SECRET`** (the `|| 'fallback-secret'` default — which would have let anyone forge a token — is gone; `>= 16` chars required at boot, alongside the existing agent-secret and encryption-key checks). The **committed dev JWT was removed** from `frontend/src/api.ts` (a real leaked credential) and replaced with an env-sourced `VITE_DEV_TOKEN` (gitignored `.env.local`, no committed fallback), and **`JWT_SECRET` was rotated**, invalidating that leaked token. Added `.env.example` for both backend and frontend documenting every var. Templates stay a shared seeded catalog (global read is intentional — it's the curated library, all seeded under the placeholder user); route-level IDOR regression tests are folded into the pending real-Postgres integration suite (P1). ## Strategy guardrails (from the 2026-07-07 analysis)

- **Reliability control plane, not universal scheduler** — two excellent connectors beat six half-connectors; new connectors unlock only when sync reliability >95% and crash rate <2% hold.
- **No fake data in the UI** — an automation tool earns trust by telling the truth (status panels, upvotes, dates).
- **Dogfood**: migrate real Task Scheduler jobs onto TaskHub-created tasks; every friction point is roadmap input.
