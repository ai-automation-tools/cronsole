- **MCP server** (P3 — highest-leverage Phase-6 item; thin wrapper over existing routes): a new `mcp-server/` package exposes the TaskHub REST API to any MCP host over **stdio**, so Claude Code / Claude Desktop / Codex / Cursor can drive TaskHub in natural language. **5 tools**, each a thin call through a small axios client (`src/client.ts`) into an existing route — no new business logic, so owner scoping, no-shell `{executable,args[]}` structuring, signed agent commands, and cron→trigger conversion all stay server-side where they're already tested: **`list_tasks`** (`GET /tasks`, with client-side platform/status/category/search filters), **`run_task`** (`POST /tasks/:id/run`), **`list_templates`** (`GET /templates` — surfaces each template's id, tags, target platforms, default schedule, and declared `{{placeholder}}` params so an agent can discover what to fill), **`create_task_from_template`** (`POST /templates/:id/apply` — server fills placeholders from raw `parameters`, converts the cron, registers via the signed agent; gated to the creatable platforms Windows + TaskHub-native), and **`convert_schedule`** (`POST /tasks/preview` — validate/convert a 5-field UTC cron to a native trigger with a 0–1 confidence score + lossy-conversion warnings). Auth is a single user JWT via `TASKHUB_TOKEN` (`Authorization: Bearer`), base URL via `TASKHUB_API_URL` — the server acts entirely as that one user (a per-user pairing flow replaces the hand-minted token once the Go-public account system lands). Honest failures: the client normalizes an API error into the backend's own message + status (`Task not found`, `HTTP 409 …`) and every tool returns `isError: true` rather than throwing; all logging goes to stderr so stdout stays a clean JSON-RPC stream. Built on the stable `@modelcontextprotocol/sdk` 1.29 (`McpServer` + `StdioServerTransport`, zod input schemas), TypeScript strict/ESM matching the backend. **Deliberately not wired into the repo's root `.mcp.json`** — that's Claude Code's dev tooling; this is a product component users point their own host at (README documents `claude mcp add` + Claude Desktop JSON). Verified live end-to-end against the running backend: MCP handshake + `tools/list` shows all 5; `list_tasks` returned 285 real tasks, `list_templates` surfaced git templates with correct per-param names, `convert_schedule` handled a valid cron (confidence 1 + trigger) and an invalid one (score 0 + warning), and the dummy-token path surfaced the real `HTTP 403 Invalid or expired token`. `tsc` build clean. Side-effecting tools (`run_task`, `create_task_from_template`) were not fired live to avoid running/registering real Windows tasks — identical plumbing to the verified read/preview paths. *(2026-07-13)*

## Strategy guardrails (from the 2026-07-07 analysis)

- **Reliability control plane, not universal scheduler** — two excellent connectors beat six half-connectors; new connectors unlock only when sync reliability >95% and crash rate <2% hold.
- **No fake data in the UI** — an automation tool earns trust by telling the truth (status panels, upvotes, dates).
- **Dogfood**: migrate real Task Scheduler jobs onto TaskHub-created tasks; every friction point is roadmap input.

### Core model

Every automation is three interchangeable parts — **Trigger → Action → Execution Target** (e.g. *every weekday 07:00 → run PowerShell script → Windows Task Scheduler*). TaskHub exposes one consistent UI and compiles the abstract template to the chosen target's native config. Long-term flow: choose **what** to automate → configure the template → choose **where** it runs → TaskHub generates the native config. Per-task **execution settings**: identity, timeout, retries, concurrency, notifications, logging, governance.
