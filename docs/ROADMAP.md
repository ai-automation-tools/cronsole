**The old front-door subdomain is retired rather than redirected**, decided 2026-07-31. It was kept briefly on the expectation that GitHub would forward it, and it does not — Pages redirects only `<user>.github.io/<repo>` to the configured custom domain, never a second custom domain pointed at the same IPs ([#34](troubleshooting/README.md#34-the-old-custom-domain-404s-after-moving-a-pages-site-to-a-new-one)). The alternative — a minimal second repo holding the old `CNAME` with a `<meta refresh>` + `<link rel="canonical">` — buys nothing here, because the site predates public launch and the URL was never advertised. **A name that doesn't resolve reads as "gone"; one that resolves to a 404 reads as "broken"** — so deleting the record is the more honest of the two failure modes, not merely the cheaper one. The `cronsole-site` commit that made the wrong claim carries a follow-up commit correcting it, since the mistake is in that repo's public history.

- **The registry URL was moved, and that was a one-time-only opportunity.** `TEMPLATE_REGISTRY_URL` is commented out in both `backend/.env` and `.env.example`, so **zero installs were fetching it** — not even this machine, which runs the bundled catalog (deliberate, 2026-07-15). GitHub redirects renamed repos' git URLs indefinitely but **not** Pages paths, so the old path 404s immediately (verified). The same move after the first real install would be a silent outage on a schedule nobody watches. **Treat the URL as frozen from here on** — see CLAUDE.md §9 and `publish-frontdoor.ps1`, both of which previously argued for the freeze on grounds this move has now spent, and were rewritten rather than quietly left standing.
- **The front door moved to `cronsole.mikesailab.com`**, after the DNS record was confirmed resolving on two independent resolvers — flipping first takes the site down for however long propagation takes, which is why it was held rather than done with the repos. The 25 held references went with it, including the **Connect Pack** (version bumped **1.1 → 1.2**: `CONNECT_PACK_HOME` is where a reader looks for a newer copy, so changing it *is* a content change, and a downloaded pack can never update itself). **Verify a domain move by requesting the old URL and reading the status code**, not by confirming the record resolves — that assumption is what produced [#34](troubleshooting/README.md#34-the-old-custom-domain-404s-after-moving-a-pages-site-to-a-new-one).
- **The local clone directory stays `…\Live_Apps\taskhub`, permanently** — every scheduled task embeds it as an absolute path, and it is not user-visible branding. (CLAUDE.md previously said it "moves (if ever) with the stage-3 repo rename"; that is now decided and corrected.)

*2026-07-31 addendum: **Four Go-public checklist items shipped together — the launch blocker among them was a route nobody wanted.** (1) **`POST /auth/register` is deleted.** It was mounted, unauthenticated, on a service whose job is creating and running commands on your machine, so anyone who could reach `:3000` could mint themselves a real account and a valid token — and the final P3 item is specifically about making that service reachable from other devices. Deleted rather than flag-gated (a dev-only flag is one misconfiguration away from open). **Why it survived is the reusable part: the integration suite drove it for its own convenience, so the route had a constituency that wasn't a user.** Those tests now run through `/setup`, and one **pins the 404** as a tripwire. (2) **REST CORS now reads the same `ALLOWED_ORIGINS` list Socket.IO already enforced** — `createApp()` was a bare `app.use(cors())`, reflect-any-origin, while the socket channel was restricted: two mechanisms answering one question, which is how one of them quietly stops matching the other. Both now share one parser. Two calls the logged item didn't settle: a request with **no `Origin` header is always allowed** (every non-browser caller — MCP server, `curl`, the suite — and CORS was never their gate), and the item's **loopback condition was dropped as unobservable** (there is no bind config to read; the container must bind every interface) in favor of *empty list stays permissive **and warns at boot***, since "unset" and "deliberately open" are indistinguishable from inside the process and only one is a decision. (3) **Both package manifests said ISC** while the `LICENSE` file, the README badge and each other said Apache-2.0 — two machine-readable license claims contradicting the repo. *2026-07-28 addendum (5): **Run history export + the automation health score shipped**, together, because three separate logged items all needed the same **bulk `ExecutionLog` query** first. **The finding that reshaped the score came before any code:** `ExecutionLog` records runs **TaskHub performed**, not runs that happened — a Windows task firing on its own schedule writes nothing, and a manual Windows run's `SUCCESS` means "the agent started it". Scoring from it would have called nearly every task on a real machine never-run, at dashboard scale. So the evidence now comes from **Windows itself** (`lastTaskResult`, `numberOfMissedRuns`, added to the read-only `task:list`; **needs an agent republish**). Three rules hold the scorer honest: score only what can be evidenced, **absence of evidence is `unknown` and never `ok`**, and the number ranks rather than grades — it never appears without its signals. The CSV names what it contains, ships UTF-8 + BOM, and **neutralizes formula injection**, because TaskHub stores command lines and a task named `=cmd|'/c calc'!A1` would otherwise make the report a live payload. **Two design bugs were found by running it on the real 354-task machine and by no test**: system tasks dominated the "needs attention" list — re-creating the very burial the Personal lens shipped that morning to prevent — and `DBG_TERMINATE_PROCESS` was being read as a failing exit code. Both fixed and pinned. New traps [#29](troubleshooting/README.md#29-prisma-migrate-refuses-to-run-migration-was-modified-after-it-was-applied--and-offers-to-drop-your-database) (an applied migration file is immutable, comments included — and Prisma's only offered remedy drops the database) and [#30](troubleshooting/README.md#30-a-route-500s-on-real-data-while-tsc-is-green--a-cast-on-a-query-result) (a cast on a query result is a promise the query cannot keep). *2026-07-28 addendum (4): **Restore shipped — the backup story finally closes.** Bulk export landed earlier the same day and restore did not, which left the Tools tab able to tell you 56 tasks were gone and hand you a folder of XML, and unable to put one back. Delivered as a new **signed** agent verb (`task:import`), `POST /api/tools/restore/tasks`, and a Restore card on the Tools tab. **The design point that mattered most was not in the logged item:** the route always computes a **plan** first — create / overwrite / skip / refuse per file — from the machine's real tasks and folders, and both of those are readable through **read-only** verbs that already shipped. So `dryRun` is a genuine preview rather than a rehearsal, the count arrives before the click, and the preview works even against an agent that has not been republished. Three decisions carried through as designed: overwrite **refused by default** (an existing task reports the third state `exists` — not a failure, not a success — enforced by Windows' own `TaskCreation.Create`, not merely by our check); the **XML signed by sha256** because the XML *is* the task, its action, its trigger, and the account it runs as; and a deliberate, opt-in, always-reported **carve-out** to "TaskHub creates exactly one folder", since a restore is the user asking for their own tree back by name rather than TaskHub littering folders nobody asked for. **Verified live after an agent republish, reading Windows rather than TaskHub**: a probe task round-tripped with its principal intact (`UserId=mikes LogonType=Interactive RunLevel=Limited` — settling the one thing unit tests could not, that `TaskLogonType.None` preserves the XML's own principal), a second restore returned `exists` with the registration date **unchanged**, overwrite returned `replaced`, and a real `\Microsoft\Windows\Defrag\` export was refused with Defrag untouched. **The live pass also found the real cost of the folder carve-out** ([#28](troubleshooting/README.md#28-a-restored-task-or-the-folder-it-landed-in-cant-be-deleted-access-is-denied)): the agent is elevated, so a task it restores and any folder it creates carry an administrator ACE — the user who created the original unelevated **could not delete the restored copy**, and the empty folder needed an elevated prompt. The invariant's original rationale called a created folder "a one-way door only the user can close"; it is in fact a door **only an administrator** can close. The design stands, and the UI now says so before the click. Coverage: backend 361 unit + 8 integration against real Postgres, agent 151, frontend 145; four mutation checks. New traps: [#27](troubleshooting/README.md#27-a-route-that-takes-an-upload-413s--and-raising-the-global-body-limit-is-the-wrong-fix), [#28](troubleshooting/README.md#28-a-restored-task-or-the-folder-it-landed-in-cant-be-deleted-access-is-denied). *2026-07-27 addendum: **A local outage traced to a boot-order race, fixed structurally in two places** (infra; not a planned roadmap item, logged here because it changed how the stack starts). Reported as "TaskHub is giving me a network error": every container read `Up`, the UI loaded fine, and nothing served `:3000` for ~12 minutes. **Nothing waited for Postgres to be *ready*, only to *exist*** — after an unclean shutdown it spends seconds in crash recovery refusing connections, and the boot seed dies on the refusal. It bit **both** backends with different error strings (container: `FATAL: the database system is starting up`; host: `Can't reach database server at localhost:5432`). What made it permanent rather than transient is the supervisor: **`tsx watch` survives the crash**, so the container never exits and `restart: unless-stopped` never fires, while Docker's port proxy holds `:3000` with nothing behind it. **Compounding cause: two stacks were running at once** — this repo runs backend/frontend on the **host** (`scripts/taskhub.ps1`; Docker is db+redis only), but a stray full `docker compose up -d` had started rival containers; the container took `:3000`, the host backend then couldn't bind it, and once the container died the port was held by a corpse — while `taskhub.ps1`'s `Test-Port 3000` liveness check reported **"backend already up"** and refused to start the real one. Every layer reported something true and the sum was a lie. Fixed with a `pg_isready` healthcheck + `condition: service_healthy` (container), a new `Wait-Db` in `taskhub.ps1` (host), and **`profiles: ["docker"]` on backend/frontend** so a plain `docker compose up -d` is db+redis only and cannot create a rival stack (`docker compose --profile docker up -d` for the containerized variant). The frontend also moved off Vite's default `5173` → **`7373`** with `strictPort`, since the collision was between the repo's own two copies. ### Reliability & product sprint (July 2026)

- **Per-command nonce on signed agent commands — a legitimate re-send is no longer eaten by the replay guard** (P3; the fix for [troubleshooting #16](troubleshooting/README.md#16-a-second-identical-agent-command-within-one-second-is-dropped)): `ts` is second-granular and was the only varying field, so two identical commands inside one second produced a **byte-identical message and signature**. The agent's replay guard — correctly — cannot distinguish that from a captured frame, so it dropped the second one **silently**, and the backend, having no reply, timed out after 15s and reported `Agent trigger timeout`: the transport blamed for a clock-resolution problem. User-visible as a double-clicked **Run Now** hanging 15s. Fixed by putting a fresh 16-byte **nonce inside the signed message**, immediately before `ts`, in all six commands (`emitSignedCommand` generates it; `signCommand` takes it as a parameter exactly as `ts` does, keeping the golden vectors deterministic). **Inside** the signature, not merely alongside — an unsigned nonce could be rewritten in flight to turn a replayed frame into a "fresh" command, the same reasoning that already puts `folder` and `trigger` under the signature. **The replay cache needed no change**: keyed on `(ts, sig)`, it stops colliding on its own once the signature is unique per instance; the `*Message` helpers take the nonce as a **required** parameter, which is the enforcement that one always exists. No back-compat shim — backend and agent ship together by design, so an optional nonce would mean two valid message forms, weakening the guarantee to serve a skew the project doesn't support; a skewed agent fails closed. **Cross-language golden HMAC vectors regenerated**, and — per the established practice — the generator was first validated by **reproducing the previously-committed vectors from the old format**, because a generator that can't reproduce what's already in the repo emits new values that are confidently wrong and then get pinned by both suites (a lie agreed on twice). Raw params are validated server-side against the template's declared parameter definitions (required non-blank, `select` ∈ options, undeclared keys / non-string values rejected — each a specific 400). The resolved `{executable, args[]}` rides `CreateTaskOptions.action` to the Windows connector (no re-tokenization; still covered by the task:create HMAC), non-argv platforms (native HTTP jobs) get whole-string substitution, and the legacy pre-substituted `command` body field still works (deprecated). No agent change needed. **Verified end-to-end live**: applied the PowerShell Script starter from the browser with a spaced path → registered as one quoted `-File` arg; probed with `scriptPath = C:\nonexistent\x.ps1" & calc.exe` → registered as a **single backslash-escaped argument** to powershell.exe (no second process possible); API probes confirmed all four 400 paths. Noted while verifying (existing behavior, already backlogged in the P2 Apply-modal task-name item): re-applying a template with the same name silently overwrites the existing Windows task. - **Structured command handling — no more `cmd.exe /c` shell wrap** (fourth P0 blocker done → **P0 security complete**): the agent registered every created task as `new ExecAction("cmd.exe", "/c " + command, null)` — the whole command string ran through a shell, so a template parameter substituted into it (e.g. a `{{scriptPath}}` of `x.ps1 & calc.exe`) was interpreted by cmd = command injection / RCE on the user's machine. Now the backend structures the resolved command into `{ executable, args[] }` server-side (`utils/commandParser.ts`, a quote-aware tokenizer) and the agent registers a **direct ExecAction** — no shell — quoting each argument by Windows `CommandLineToArgvW` rules (`ArgumentQuoting.cs`). Because no shell parses the line, a malicious parameter can at worst become a malformed argument to the *intended* executable; it can never launch a second process. The structured action is **covered by the task:create HMAC signature**: the signed message gained an action-canonical field (executable + args joined by 0x1F), computed identically on both sides and pinned by the shared cross-language golden vector (backend Vitest + agent xUnit both assert the new `createSig`). The `ITaskScheduler.CreateTask` contract now takes an `AgentExecAction` instead of a command string; commands that genuinely need shell features name the shell explicitly (two Tier-B seed patterns updated: `pg_dump … > backup.sql` and `del /q %temp%\\*` now use `cmd.exe /c "…"`). **Breaking** — agent + backend must be deployed together (the create signature changed). - **Multi-tenancy route scoping + JWT fail-fast + dev-JWT rotation** (third P0 blocker done): the task API previously ran as a single hardcoded `cli_user_placeholder` and, worse, its by-id routes looked tasks up by `id` alone — so any authenticated caller could **list every user's tasks** (`GET /tasks` had no `where`), and read/patch/delete/**run** *anyone's* task by guessing an id (IDOR → the run path is remote command execution on another user's agent).   ### Tool 1 — Mass export / backup of Windows Task Scheduler tasks

  Export **all** tasks, or **all tasks in one folder**, as native Task Scheduler XML, to a location the user picks. Per-task export already exists (`GET /api/tasks/:id/export`, MCP `export_task`); this is the bulk case, and it is the **missing half of a disaster-recovery story we already know we need**: the bulk-clear item below exists because *one* deleted Task Scheduler folder can flag **56 tasks MISSING at once**. Today that is an unrecoverable loss — TaskHub can tell you the tasks are gone and let you clear the rows, but it cannot give you the tasks back.

  **The load-bearing finding — this needs no agent protocol change.** `task:export` (`agent/TaskHub.Agent/AgentService.cs:288`) takes a raw `taskPath` and calls `_scheduler.ExportTaskXml(taskPath)`; it is **read-only and unsigned** (like `task:list`) and it does **not** check that the path belongs to a TaskHub-tracked task. `WindowsAgentConnector.exportTask` (`backend/src/connectors/WindowsAgentConnector.ts:166`) passes `externalId` straight through as `taskPath`. So the agent can already export **any** task on the machine — the restriction to tracked tasks lives entirely in the backend route, which is keyed on a DB row id. Combined with `/discover`, which already enumerates every task with its path, "export everything in every folder" is **backend + frontend work only**. A batched `task:exportBatch` verb is an *optimization* (see the timeout note below), not a prerequisite — and optimizations don't need an agent republish.

  Design points, each of which has already bitten somewhere in this repo:
  - **Exclude `\Microsoft\` by default.** On a real machine the split is **95 user tasks across 13 folders vs. 257 `\Microsoft\` system tasks** (measured during the untracked-tasks work). Dumping 352 files by default buries the 95 that matter. Same call as that item: surface the system count, don't fold it into the total.
  - **Decide tracked-only vs. whole-machine, and say which.** Tracked-only reuses the existing route per task. Whole-machine (what was asked for) exports tasks TaskHub has no row for — strictly more useful as a backup, and now known to be cheap. Whichever ships, the UI must state which it did; "Export all" meaning "all the ones we happen to have imported" is exactly the invisible-fence problem the untracked-tasks item was filed for.
  - **Zip on the server, not in the browser.** Task Scheduler XML is delivered **UTF-16 LE + BOM** because that is the only encoding Windows re-imports. Shipping those bytes to the frontend as JSON strings and zipping client-side walks straight into the trap MCP `export_task` already hit, where axios decoded UTF-16 as UTF-8 into mojibake and needed a raw-bytes client path. Build the archive server-side where the bytes are still bytes.
  - **The 15s timeout is per-call** (`WindowsAgentConnector.ts:194`). 95 sequential round-trips is a long silent wait and 352 is worse; needs concurrency or a batch verb, **plus a progress signal** — the `task:exported` handler already correlates by `taskExternalId`, so concurrent in-flight exports work without protocol changes.
  - **"Browse for a location" has a hard browser limit.** A web page cannot write to an arbitrary filesystem path. The honest implementation is the **File System Access API** (`showDirectoryPicker()`) — a real folder picker, Chromium-only but `localhost` is a secure context, so it works for a local-first app — with a **single-ZIP download fallback** everywhere else.
  - **Do NOT solve the picker by adding an agent file-write verb.** It is the tempting shortcut (the agent is already on the machine, already elevated, and could just write where told), and it would convert a task-scheduler agent into a **general elevated arbitrary-file-write primitive** reachable from the backend. That is a categorically larger attack surface than everything the agent does today, traded for a directory picker. The browser limitation is worth living with.
  - **Exported XML contains full command lines, arguments, and the principal each task runs as.** One task at a time is one thing; a whole-machine dump into a folder is a different exposure — say so at the point of export rather than silently writing 95 files that may contain API keys in `argv`.

  **Export is half a backup — restore is the natural phase 2** and should be named now so it isn't discovered later: Windows re-imports via `schtasks /create /xml` / `Register-ScheduledTask`, and the UTF-16 output is already restore-ready by construction. Not in this slice; do not let the slice pretend to be a backup product without it. *(Now tracked separately — see **Restore tasks from an export** below.)*

Windows enforces it too (`TaskCreation.Create` refuses rather than our existence check racing), because the platform, not TaskHub, is the witness that matters.
  - **The XML is signed by hash, not by value.** The XML *is* the task — action, trigger, and principal (including `RunLevel Highest` and the run-as account) — so an unsigned XML would make the signature decorative. It enters the canonical message as a lowercase-hex **sha256 over its UTF-8 bytes**, mirroring how `canonicalizeAction` / `canonicalizeTrigger` reduce a structured field to a fixed, unambiguous string on both sides of the language boundary.
  - **Missing folders are recreated, opt-in and reported — a deliberate carve-out to "TaskHub creates exactly one folder".** That invariant exists because folder deletion needs elevation, so a folder TaskHub creates is a one-way door only the user can close; it was written after a template apply left three empty folders nobody asked for. Restore is the opposite consent situation: the user is asking for *their own* folder tree back, by name, from a file they chose. Refusing would be correct by the letter and useless in practice — a restore onto a reinstalled machine would refuse every task in the archive. So: a **Recreate missing folders** checkbox (signed, like `overwrite`), and the result **names every folder it created**. The invariant is amended rather than abandoned — TaskHub still creates nothing unasked, and `\TaskHub` is still the only folder it ever *removes*.
  - **The preview needs no agent write, which is why it can exist at all.** The route always computes a **plan** first — per file: `create` / `overwrite` / `skip` (exists) / `refuse` (bad XML, `\Microsoft\`, missing folder with the checkbox off) — from the two **read-only** verbs that already ship (`task:list`, `task:folders`). `dryRun: true` returns the plan and writes nothing, so the count arrives *before* the click rather than after it (the same principle the *Import defaults* item is filed for). It also means the preview works against an agent that has not been republished yet.
  - **Target path resolution is manifest › the XML's own `<URI>` › the relative file path**, in that order, and the resolved path is shown for every file in the plan. Our own archives carry the manifest, so they are exact; a hand-supplied file falls back to what Windows itself wrote into the XML; the filename is a guess and ranks last precisely because `safeSegment` sanitization made it lossy on the way out.
  - **Scope is Windows XML only.** The bulk export it pairs with is Windows-only, so a TaskHub-native JSON restore is *not* in this slice — stated rather than silently absent.

- [ ] **Template registry — decouple the catalog from the repo** (architecture direction, decided 2026-07-13): templates are fast-moving *content*; the app is stable *code* — so stop baking the catalog into `seed.ts` + a Postgres reseed and instead serve it from a **decoupled registry** the app fetches at runtime. Two decided pieces:

A template describes the automation abstractly along the **Trigger → Action → Execution Target** model (see the *Template & scheduler catalog* reference appendix at the end of this doc), carrying `schemaVersion`, the existing `{{placeholder}}` `parameters`, an abstract `trigger` (cron/interval/event) and `action` (`{executable, args[]}` / http job), `compatibleTargets`, and `execution` settings (timeout/retries/runLevel).   **The three open questions are now settled** *(decided 2026-07-15)*. They were the real work; the wrappers are mechanical.

  **(1) Destructive-op gating → tier it, and gate only the irreversible verb.** Read-only (`get_task_history`, `export_task`) and *reversible* verbs (`set_task_status`, `update_task_schedule`, `update_task_action`) register unconditionally. **`delete_task` registers only when `TASKHUB_MCP_ALLOW_DESTRUCTIVE=true`** — and when it's off the tool is **absent from `tools/list`**, not present-and-erroring, so the model never plans around a capability it doesn't have.

  The reasoning that picked env over the alternatives: **a `confirm: true` parameter is not a gate**, because the model fills it in itself — it's the caller asserting to itself that it's sure, which is exactly the deliberation that's missing. An env var is **out-of-band**: the human sets it, and no amount of agent reasoning reaches it. That's the same posture the agent already takes toward *its* caller (`\Microsoft\` is refused **in the agent** as well as the backend, because the agent holds the elevation and cannot trust who's asking) — the MCP server is one more untrusted caller, so the gate belongs somewhere the caller can't touch.

  Gating *every* mutating verb was rejected for conflating **irreversible** with **reversible**: `set_task_status` is the honest way to park a task, and gating it pushes an agent toward the worse workaround of encoding "don't run" in the cron — [#14](troubleshooting/README.md#14-a-rare-cron-becomes-an-hourly-trigger) exactly. A gate that makes the safe path harder than the unsafe one is worse than no gate.

  **(2) Tool-count creep → one tool per verb** (7 → 14; `create_native_task` is additive, not a fold-in of `create_task`, since `POST /tasks/native` takes a full job spec where `POST /tasks` takes a command string). Collapsing the three `update_*` into one mode-flagged tool saves ~2 tools and costs the thing that makes these tools *safe*: a mode-flagged tool needs one description covering every mode, so the per-verb warnings dilute precisely where they matter most. **The descriptions are the safety mechanism** — an agent reads them, not this roadmap. Revisit if host context pressure ever makes the count a real problem.

  **(3) Low-confidence schedules → fix the warning, don't refuse in the wrapper.** Refusing below a threshold would put a policy decision in `mcp-server/`, which §11a forbids and which would protect only MCP callers while the UI and Apply kept the same silent replacement. The **backend fix** (the *fallback warning names the frequency* item below) fixes it once for every caller. `create_task`'s description already tells the model to read the returned trigger rather than the score.

  **(b) The skill must teach it. ✅ Shipped 2026-07-15** — [`skills/taskhub/references/task-authoring.md`](../skills/taskhub/references/task-authoring.md), in the same change as `create_task`, per the mirror-surface rule. The two AI surfaces are complements, not duplicates: the MCP server is the *hands*, the skill is the *judgment*. Shipping (a) without (b) gives an agent a `create_task` tool and no idea that schedules are **5-field cron in UTC**, that `\Microsoft\` is refused, that a folder must **already exist**, that a `0.7` confidence means the schedule was *replaced* rather than nudged, or that a green suite is not evidence a command runs — it would confidently create wrong tasks, the exact failure mode §11a exists to prevent. The guide covers the six creation paths and when each is right, command recipes per kind of work (script / direct exe / explicit shell opt-in / HTTP / npm / Python / Docker / unattended CLI agent), quoting, folders, the disable-don't-cron rule, an MCP-vs-REST capability table, and how to verify from **outside** TaskHub. **Extend it as the tools below land** — the table in §5 is the honest record of what MCP can't do yet and must not go stale.

- [x] **Signed agent commands carry a nonce — a legitimate re-send inside one second is no longer dropped as a replay** *(found 2026-07-15 while verifying the MCP management verbs; **shipped 2026-07-15** — see Completed; [troubleshooting #16](troubleshooting/README.md#16-a-second-identical-agent-command-within-one-second-is-dropped))*: `ts` is **second-granular** and the signature covers `(message, ts)`, so two identical commands to the same task inside one second are **byte-identical** — indistinguishable from a captured packet replayed. The agent's replay guard drops the second, silently and *correctly*; the backend then times out after 15s and reports `Agent trigger timeout`, blaming the transport. Reproduced cleanly: run #1 39ms OK, run #2 (+0.3s) 15,032ms timeout, run #3 (+1.5s) 21ms OK — same task, only the clock changed.
  - **User-visible today**: double-clicking **Run Now**, or any script/agent driving two runs quickly, eats a 15s hang and a misleading error.
  - **The fix is uniqueness, not chattiness.** Add a **nonce** to the signed message so a legitimate re-send is never byte-identical, while a true replay (same nonce ⇒ same signature) is still caught. **Do not "fix" it by making the agent answer a rejected command** — the silence on an unverifiable command is a deliberate security property; the bug is that a legitimate command can *look* unverifiable.
  - Scope: a **protocol change across both languages** — backend `emitSignedCommand`, the C# `AgentAuthenticator` message builders, and the **cross-language golden HMAC vectors** move together, plus an agent republish.
  - **Design decided 2026-07-15 (before implementing):** the nonce goes **inside the signed message**, in a fixed position immediately **before `ts`**, for all six commands — so it is covered by the signature and cannot be stripped or rewritten in flight by an on-path attacker (the same reason `folder` and `trigger` are signed). Generated per-emit in `emitSignedCommand` (16 random bytes, hex), passed to `signCommand` as a parameter exactly as `ts` already is, so the golden vectors stay deterministic.
  - **The agent's replay cache does not change.** It is keyed on `{ts}|{sig}`, and once the nonce is in the message the **signature is already unique per command instance** — two legitimate runs differ, a replayed frame is byte-identical and still collides. The enforcement that a nonce always exists lives in the `*Message` helpers, which take it as a **required** parameter: you cannot build a signed message without one.
  - **No back-compat shim.** Backend and agent ship together (a mismatched message string rejects every command, by design), so an optional nonce would create two valid message forms — weakening the guarantee and doubling the test surface — to serve a version skew the project doesn't support. A skewed agent fails closed and loudly.

Signals that cannot exist for a platform (duration drift for a fire-and-forget Windows trigger) are **absent**, never defaulted to healthy.

  - **The number ranks; it does not grade.** Each signal carries a fixed weight and the score is `100` minus their sum, so it is explainable rather than tuned — its job is to sort 352 tasks worst-first, which needs a scalar.   **(1) Postgres is the fork in the road.** `docker-compose.yml` runs `postgres:16-alpine`, and Docker Desktop cannot be a dependency of a consumer installer. Two honest paths:
  - **Bundle Postgres binaries** — EnterpriseDB portable zip, `initdb` into `%ProgramData%\TaskHub\pgdata` on first run, registered as a service on a non-default port. **Zero code change; dev/install parity preserved.** Costs ~250 MB and a real support surface: port conflicts, failed `initdb`, orphaned data directories on uninstall.
  - **Migrate to SQLite** — one file, no service, dramatically better install UX. **Not a provider flip:** `Template.tags String[]` (`backend/prisma/schema.prisma:123`) is a Postgres scalar list with no SQLite equivalent, so it needs a schema change plus a migration — and `npm run test:integration` is written against real Postgres, so the test infra either forks or runs both providers.
  - **Lean: bundle Postgres for v1.** It ships without touching the data model or the test suite, and SQLite stays available if install weight ever becomes an actual complaint. Tracked in **Open decisions**.

  **(2) Redis just goes.** It is already optional for single-instance; cut it from the installed stack entirely.

  **(3) The frontend must stop being a dev server.** Today it is `vite` on `:7373` with `VITE_API_URL` pointing at `:3000`, and the backend serves **no static files at all** (no `express.static` in `backend/src/index.ts`). Installed, it should be `vite build` → static assets served by Express on **one** port, same-origin — which also removes the `ALLOWED_ORIGINS`/CORS dance from the installed config. Small, but genuinely new code.

  **(4) Runtimes.** Ship `node.exe` + `backend/dist` + `node_modules` (pin Prisma `binaryTargets` so the Windows query engine is present). The agent is the easy half — already a `WinExe` with a startup script (`agent/setup-agent-startup.ps1`) — but `TaskHub.Agent.csproj` declares no `RuntimeIdentifier`/`SelfContained`, so it is **framework-dependent**: the installer either chains the .NET 10 runtime or the agent publishes self-contained (+~70 MB).

  **Two things that must be designed in, not bolted on:**
  - **Secrets are generated per machine, at install time.** `JWT_SECRET`, `ENCRYPTION_KEY`, and `AGENT_PAIRING_SECRET` carry dev defaults in compose. Baking fixed values into an installer would give **every install on earth the same JWT signing key and the same pairing secret** — anyone could mint a valid token for anyone else's instance, and pair an agent to it. Generate into an ACL'd `%ProgramData%\TaskHub\.env` on first run.
  - **Uninstall must sweep Task Scheduler.** TaskHub creates real OS state under `\TaskHub\`. Removing the app while leaving live scheduled tasks running is the worst outcome available — that is a `task:delete` sweep at uninstall time, and it needs elevation.

  **Packaging choice:** the agent item above specifies WiX MSI; for a *multi-payload app* installer, **Inno Setup** or **Velopack** reaches a working signed `.exe` far faster than WiX Burn, and Velopack brings the update channel *Agent distribution & trust* already wants. The outer `.exe` can chain the agent MSI rather than replace it.

  **Expect SmartScreen.** An unsigned installer that registers a service and writes to Task Scheduler is precisely the flagged profile, so the OV/EV Authenticode certificate under **Agent distribution & trust** is a hard prerequisite here, not a polish item.

  **Rough scope:** ~1 week to something installable on a clean machine; ~1 more to make it *trustworthy* (signing, uninstall correctness, a first-run wizard for the owner account + agent pairing). Largest unknown: embedded-Postgres lifecycle on machines you don't control.

The frontend, backend, Postgres, and agent all stay on the user's machine; **only the dashboard view is exposed remotely**, over a private, access-controlled channel — never nakedly on the public internet. Current lean: **bundle Postgres for v1**, revisit SQLite only if install size or support load makes it worth the migration.
- [x] **Default theme: dark, or follow the OS?** *(opened 2026-07-28; **resolved 2026-07-28 — dark**)*: `useTheme.readStored()` now falls back to `'dark'`, with `system` kept as an explicit third choice. - [x] **Does untrack need an exclusion memory?** *(opened 2026-07-28; **resolved 2026-07-28 — yes, remember the exclusion**)*: shipped as `TaskExclusion`, keyed on the platform-native `externalId`. The alternative (untrack implies you stop importing the whole category) was rejected as useless for one noisy task in a folder you want. The way back is an explicit category import, which clears the exclusions inside it and **says so before and after**. See the P2 item.

## Strategy guardrails (from the 2026-07-07 analysis)

- **Reliability control plane, not universal scheduler** — two excellent connectors beat six half-connectors; new connectors unlock only when sync reliability >95% and crash rate <2% hold.
- **No fake data in the UI** — an automation tool earns trust by telling the truth (status panels, upvotes, dates).
- **Dogfood**: migrate real Task Scheduler jobs onto TaskHub-created tasks; every friction point is roadmap input.

## Appendix — Template & scheduler catalog (backlog reference)

> Folded in from the 2026-07-13 template/scheduler strategy pass (the exploratory doc has been retired into this appendix). This is the **content backlog** the [Template registry](#-p2--product-value) will hold — the abstract catalog can grow freely via the registry, but **execution targets unlock only when reliable** (reliability-control-plane guardrail). The concrete near-term commitment is the **MVP starter set** + the **Windows** compiler; everything below it is a prioritized reference, not committed scope.

### Core model

Every automation is three interchangeable parts — **Trigger → Action → Execution Target** (e.g. *every weekday 07:00 → run PowerShell script → Windows Task Scheduler*). TaskHub exposes one consistent UI and compiles the abstract template to the chosen target's native config. Long-term flow: choose **what** to automate → configure the template → choose **where** it runs → TaskHub generates the native config. Per-task **execution settings**: identity, timeout, retries, concurrency, notifications, logging, governance.
