### Security hardening (July 2026)

- **Integration test suite against real Postgres** (P1 QA — first slice; carries the IDOR regression tests deferred from P0): a new backend integration harness runs the *real* Express routes (via supertest) and services against a *real* Postgres, separate from the mock-Prisma unit suite. `src/app.ts` was extracted (`createApp()` — middleware + routes + error boundary) so tests drive the app without opening the agent socket or starting the native scheduler; `index.ts` still owns the HTTP/Socket.IO server and bootstrap. A dedicated `vitest.integration.config.ts` (serial, single fork) points at a `taskhub_test` database that `globalSetup` creates + `prisma migrate deploy`s, with a `beforeEach` TRUNCATE for per-test isolation; `*.integration.test.ts` is excluded from the unit config so `npm test` stays DB-free, and `npm run test:integration` runs the new suite (wired into CI with a Postgres service). **21 tests**: the **IDOR/multi-tenancy regressions** (the P0 deferral — user B gets 404 on GET/PATCH/DELETE/run/executions of user A's task, and mutations genuinely don't land; `GET /tasks` is owner-scoped; unauthenticated → 401), the **auth flow** (register → token authenticates a protected route; wrong password 401; duplicate email 400; Zod weak-password/bad-email 400), **config encryption at rest** (a config written through `serializeConfig` lands as `iv:tag:ciphertext` in the raw DB column with the plaintext secret absent, round-trips back, rejects a tampered payload, and still reads legacy plaintext object rows), and **data flow** (native-create computes a real `nextRunTime`; `TaskService.upsertTasks` persists a 250-task sync across batched `$transaction`s in order and idempotently; `removeStaleTasks` prunes). Audit finding surfaced while writing these: the archived Test_Plan's `429` login rate-limit isn't implemented (tracked in Go-public). Remaining QA: Playwright E2E, soak/resilience, security audit + perf report. Backend unit 121 + integration 21. *(2026-07-10)*
- **Agent-auth hardening follow-ups** (closes the three residuals from the 2026-07-09 WebSocket-auth review): **(1) the `task:create` trigger is now signed.** The HMAC message gained a canonical trigger field (`canonicalizeTrigger` in `utils/scheduler-conversion.ts` / `AgentAuthenticator.CanonicalizeTrigger` in C# — a fixed-order pipe-joined form, null → `"none"`), so an on-path attacker on a plaintext connection can't rewrite a task's *schedule* in flight any more than its command. The agent parses the trigger *before* verifying and includes its canonical form in the checked message; the shared cross-language golden vector gained a null-trigger and a Weekly-trigger create case. **(2) Per-command replay guard.** The agent now rejects a `(ts, sig)` it has already accepted within the freshness window (bounded, self-pruning cache mirroring the server's handshake nonce cache), so a captured command frame can't be replayed on a plaintext link. **(3) Session-key reconnect overlap.** The agent kept a single mutable session key, so a command signed under the old connection that was still in flight when the socket rekeyed was false-rejected; it now keeps the current key (non-expiring) plus any superseded key for a `MaxSkew` grace window and verifies against either. A **latent bug caught in live verification**: the first cut expired *every* key after 120s, which silently broke all commands on any connection older than two minutes (the unit tests all verified within the window, so they passed) — fixed so the current key never expires. `emitSignedCommand`'s `extra` param was dropped (trigger is now a first-class signed field). **Breaking** — the create signature changed, so agent + backend must deploy together; the agent was republished for verification. Verified live end-to-end: rebuilt both sides, created a Windows task with a real Daily trigger (registered with the correct trigger + args), and ran a signed `task:run` **>120s after the handshake** to confirm the long-lived-key fix. Backend 121 tests (+3 trigger-canonical), agent 56 tests (+10: trigger canonical, replay, rekey-overlap, tampered-trigger-rejected). *(2026-07-10)*
- **Server-side per-token template substitution** (P1 command-handling follow-up — closes the last structured-command residual): the Apply modal used to substitute `{{placeholders}}` client-side and send the finished command string, which the backend then tokenized — so a parameter value with an unbalanced quote could split into extra literal args (harmless without a shell, but not what the author wrote). Now the client sends **raw parameter values** and the backend owns substitution (`backend/src/utils/templateCommand.ts`): the template is tokenized *first* (a new quote-tracking `parseCommandTokens` in `commandParser.ts`), then values substitute per-token — a quoted/composite placeholder (`-File "{{scriptPath}}"`, `--flag={{v}}`) is always exactly **one argument** regardless of its contents, while a bare placeholder token (`{{args}}`) keeps its intended multi-arg semantics, contained to that position. Raw params are validated server-side against the template's declared parameter definitions (required non-blank, `select` ∈ options, undeclared keys / non-string values rejected — each a specific 400). The resolved `{executable, args[]}` rides `CreateTaskOptions.action` to the Windows connector (no re-tokenization; still covered by the task:create HMAC), non-argv platforms (native HTTP jobs) get whole-string substitution, and the legacy pre-substituted `command` body field still works (deprecated). No agent change needed. **Verified end-to-end live**: applied the PowerShell Script starter from the browser with a spaced path → registered as one quoted `-File` arg; probed with `scriptPath = C:\nonexistent\x.ps1" & calc.exe` → registered as a **single backslash-escaped argument** to powershell.exe (no second process possible); API probes confirmed all four 400 paths. Noted while verifying (existing behavior, already backlogged in the P2 Apply-modal task-name item): re-applying a template with the same name silently overwrites the existing Windows task. Backend 116 tests (+23: `templateCommand` suite), frontend 45. *(2026-07-10)*
- **Structured command handling — no more `cmd.exe /c` shell wrap** (fourth P0 blocker done → **P0 security complete**): the agent registered every created task as `new ExecAction("cmd.exe", "/c " + command, null)` — the whole command string ran through a shell, so a template parameter substituted into it (e.g. a `{{scriptPath}}` of `x.ps1 & calc.exe`) was interpreted by cmd = command injection / RCE on the user's machine. Now the backend structures the resolved command into `{ executable, args[] }` server-side (`utils/commandParser.ts`, a quote-aware tokenizer) and the agent registers a **direct ExecAction** — no shell — quoting each argument by Windows `CommandLineToArgvW` rules (`ArgumentQuoting.cs`). Because no shell parses the line, a malicious parameter can at worst become a malformed argument to the *intended* executable; it can never launch a second process. The structured action is **covered by the task:create HMAC signature**: the signed message gained an action-canonical field (executable + args joined by 0x1F), computed identically on both sides and pinned by the shared cross-language golden vector (backend Vitest + agent xUnit both assert the new `createSig`). The `ITaskScheduler.CreateTask` contract now takes an `AgentExecAction` instead of a command string; commands that genuinely need shell features name the shell explicitly (two Tier-B seed patterns updated: `pg_dump … > backup.sql` and `del /q %temp%\\*` now use `cmd.exe /c "…"`). **Breaking** — agent + backend must be deployed together (the create signature changed). Verified: backend 93 tests (+10: `commandParser` + updated vectors), agent 46 tests (+7: `ArgumentQuoting` + updated create/vector tests). Residual (P1): the backend tokenizes the *client-substituted* command, so a parameter with an unbalanced quote could split into extra literal args (harmless without a shell) — robust per-parameter server-side substitution from raw params would remove even that. *(2026-07-09)*
- **Multi-tenancy route scoping + JWT fail-fast + dev-JWT rotation** (third P0 blocker done): the task API previously ran as a single hardcoded `cli_user_placeholder` and, worse, its by-id routes looked tasks up by `id` alone — so any authenticated caller could **list every user's tasks** (`GET /tasks` had no `where`), and read/patch/delete/**run** *anyone's* task by guessing an id (IDOR → the run path is remote command execution on another user's agent). Every task route now derives `userId` from the verified JWT (`req.user.id`, via the already-mounted `authenticateToken`), and all lookups are owner-scoped: `GET /tasks` filters `where:{userId}`; `PATCH`/`DELETE`/`POST /:id/run` use `findFirst({id, userId})` (404 on a miss); `GET /:id/executions` confirms task ownership before returning logs; create/native/health/sync/discover and the template **apply** route all attribute to the token user. Backend now **fails fast on a missing/weak `JWT_SECRET`** (the `|| 'fallback-secret'` default — which would have let anyone forge a token — is gone; `>= 16` chars required at boot, alongside the existing agent-secret and encryption-key checks). The **committed dev JWT was removed** from `frontend/src/api.ts` (a real leaked credential) and replaced with an env-sourced `VITE_DEV_TOKEN` (gitignored `.env.local`, no committed fallback), and **`JWT_SECRET` was rotated**, invalidating that leaked token. Added `.env.example` for both backend and frontend documenting every var. Templates stay a shared seeded catalog (global read is intentional — it's the curated library, all seeded under the placeholder user); route-level IDOR regression tests are folded into the pending real-Postgres integration suite (P1). Verified: backend typecheck + 83 tests, frontend typecheck + 40 tests, no committed token remains in tracked files. Remaining P0: per-OS structured command handling. The **git-history secret scrub** (the old token still lives in past commits, though rotation already killed it) is tracked under Go-public. *(2026-07-09)*
- **Encrypt `PlatformConnection.config` at rest** (second P0 blocker done): the connection `config` column (which holds API keys, agent IDs, and pairing secrets) was stored as plaintext JSON — a DB dump or backup leaked every credential. It's now encrypted at the application layer with the existing (tested) AES-256-GCM helpers, funneled through a single new module (`backend/src/auth/connectionConfig.ts`): `serializeConfig()` on the way in (write), `deserializeConfig()` on the way out (read). The Prisma column stays `Json`; the encrypted payload is stored as a JSON *string* in the canonical `iv:tag:ciphertext` form, and because encrypted configs are always strings while legacy configs were always objects, the stored JS type disambiguates the two — **legacy plaintext rows keep working with no migration** while every new write is encrypted. All 6 read sites (`createTask`/`applyTemplate`/`getHealth`/`syncTasks`×2/`runTask` across `routes/tasks.ts` + `routes/templates.ts`) and both write sites (the TASKHUB_NATIVE auto-provision in `index.ts` and the Windows auto-init in `/health`) now go through the helpers — no route touches `connection.config` directly, and the stale "*In a real system, we'd decrypt the config here*" comment is gone. A tampered/wrong-key payload throws (GCM auth failure is surfaced, not swallowed). Importing the module also gives the backend **fail-fast on a missing/short `ENCRYPTION_KEY`** at boot (the key must be exactly 32 chars). Verified: backend 83 tests (was 78; +5 new `connectionConfig` cases — round-trip, empty config, legacy-plaintext passthrough, null/undefined, tamper rejection). Remaining P0: multi-tenancy route scoping + dev-JWT rotation, per-OS structured command handling. *(2026-07-09)*
- **Agent WebSocket authentication** (first P0 blocker done): the agent↔backend Socket.IO channel — previously unauthenticated, so any process reaching port 3000 could drive `task:create`/`task:run` = RCE on the user's machine — is now authenticated on both ends. Backend `io.use()` middleware (`backend/src/ws/agentAuth.ts`) verifies an HMAC-SHA256 handshake over `(agentId, nonce, ts)` against a shared `AGENT_PAIRING_SECRET` (120s freshness, constant-time compare) and **rejects unauthenticated sockets before the connection handler runs**. State-changing commands are signed with a **per-session key** derived from the handshake nonce; the .NET agent (`AgentAuthenticator.cs`) verifies every `task:run`/`task:create`/`task:set_status` and drops anything with a bad signature or stale timestamp. Socket.IO CORS restricted to `ALLOWED_ORIGINS` (empty by default — only the non-browser agent connects today). Agent config (`TASKHUB_SERVER_URL` WSS-capable, `TASKHUB_PAIRING_SECRET`, `TASKHUB_AGENT_ID`) resolves from env **or** a gitignored `agent/TaskHub.Agent/appsettings.json` (env overrides the file; `appsettings.example.json` is the committed template, copied beside the published exe so no secret needs re-exporting each run); backend fails fast without a strong pairing secret. A shared cross-language HMAC golden vector is asserted by both the backend (Vitest) and agent (xUnit) suites so the two can't drift. A multi-agent code review also caught and fixed: an unauthenticated-frame crash in the agent's `task:run` handler (parse now inside the try), a reconnect race where a stale socket's late `disconnect` unregistered the live one (now guarded by socket identity), and added a server-side handshake **nonce replay cache** (a captured handshake can't be replayed within the freshness window to displace the agent). Verified: backend 78 tests, agent 39 tests; the Windows **auto-start / self-heal scheduled task** (`\Task-Hub\TaskHubAgent` → `Start-TaskHub.ps1`) was re-published and validated end-to-end — the published agent authenticates from its bundled config and the Windows connector reports `HEALTHY`, with the 10-min idempotent launcher confirmed not to spawn duplicates. **Breaking** — live agents must be rebuilt with the secret configured. Remaining P0: encrypt `PlatformConnection.config` at rest, multi-tenancy route scoping + dev-JWT rotation, per-OS structured command handling. Documented residuals (on-path attacker on plaintext transport only — mitigated by WSS, which the agent now supports): per-command replay within the 120s window, `task:create`'s `trigger` not covered by the signature, and a narrow shared-`SessionKey` reconnect false-reject. *(2026-07-09)*

### Reliability & product sprint (July 2026)

- **Backend hygiene sweep** (P1): three long-standing structural gaps closed in one pass. **(1) Shared Prisma singleton** — 9 files each constructed their own `PrismaClient` (9 connection pools against one Postgres); everything now imports the single client from `src/db.ts` (the constructor-level mock in `TaskService.test.ts` still works unchanged). Also removed an entirely unused client in `auth/auth.ts`. **(2) One error boundary + Zod at the edges** — new `middleware/errorHandler.ts` (an `HttpError` class + a single Express error handler mapping `HttpError`→status, `TemplateParamError`→400, malformed-JSON→400, anything unexpected→logged generic 500 so internals never leak) and `middleware/validate.ts` (`validateBody(schema)` → field-qualified 400 from the first Zod issue, parsed/trimmed body replaces `req.body`). All three routers (tasks, templates, auth) dropped their per-route try/catch-500 boilerplate — handlers now throw and Express 5 forwards rejected promises to the boundary; intentional catches stay (per-connection sync/discover isolation, P2002 duplicate email). Zod schemas on every mutating body: task create / native create / patch / sync / preview, template preview / apply, auth register (email format + 8-char minimum now enforced) / login. `parameters` on apply stays schema-permissive by design — `resolveTemplateParams` owns the granular per-parameter errors. - **Browser live updates (push instead of polling)** (P1): the dashboard now reflects changes the moment they happen — an agent sync, a native scheduled run, or an edit in another tab — instead of waiting for the 45s poll or a window-focus refetch. The backend exposes a JWT-authenticated, **receive-only** Socket.IO `/ui` namespace (`ws/uiChannel.ts`), kept fully separate from the pairing-secret-guarded agent channel (default namespace) so agent auth is untouched; browser clients authenticate with the user's token and join a per-user room. `notifyTasksChanged(userId)` is called on every task mutation (create / native-create / apply-template / sync / patch / delete / run) and once per affected user after each `NativeScheduler` tick; it emits `task:updated` to that user's room only. The frontend `useLiveTaskUpdates` hook (mounted in the dashboard) connects to `/ui` with the dev token, forces the WebSocket transport (skips the HTTP long-poll), backs off gently (30s max) when the backend is down, and invalidates `['tasks']` + `['connections']` on each push. Needs the frontend origin in `ALLOWED_ORIGINS` (documented; set for local dev + docker-compose). This is *lighter* than polling: one idle socket that only carries a message on a real change. Verified end-to-end (unauthenticated connect rejected; authenticated client received `task:updated` after a `POST /tasks/sync`); backend 93 tests, frontend 46 tests, both builds green. *(2026-07-09)*
- **Local-time schedule display in the task detail view** (P1): the parsed Schedule panel showed recurring times in UTC ("Daily at 9:00 AM UTC") because cron is stored in UTC — honest but not how a user reads their own schedule. `describeCron` (`utils/schedule.ts`) now takes the Settings Local/UTC mode; in **local** mode (the default) it converts the recurring clock time to the viewer's zone and rolls the day-of-week when the conversion crosses midnight (e.g. `0 2 * * 1` — Mon 02:00 UTC — reads "Weekly on Sunday at 9:00 PM" in New York). Conversion is anchored on a `now` reference instant so it reflects the current DST offset; interval shapes (every-N, hourly) are timezone-independent and unchanged. Wired through `TaskModal` via `useSettings`. The helper is ready to also power the P2 Apply-modal schedule preview. Also fixed a latent `tsc -b` narrowing error in `TaskModal.actionInfo` surfaced while building. Frontend 46 tests (+6 local-conversion cases incl. a pinned-timezone day-roll). *(2026-07-09)*
