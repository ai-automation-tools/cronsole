# Cronsole

Cronsole is a **single pane of glass** for scheduled tasks across Windows Task Scheduler,
Claude Code Routines, and Cronsole-native HTTP jobs. It is **local-first by design** — the
frontend, backend, and agent all run on the user's own machine. There is no hosted/SaaS
instance; the Hetzner control-plane plan was dropped 2026-07-13.

**Read this first, then read the canonical doc for the area you're touching.** This skill is
a mental model, a set of invariants, and a routing table — **not** a copy of the docs. When
this skill and a repo doc disagree, **the repo wins**; fix the skill.

## The one thing to understand

Cronsole is a **reliability control plane**. Its entire value is that the state it shows is
*true* and the actions you take *actually happen*. That reframes what counts as a bug:

> **A confident lie is the worst possible failure.** A dashboard that reports success for a
> run that never happened is worse than an error, worse than a crash, worse than no dashboard
> at all. When you must choose between a graceful degradation and an honest refusal, **choose
> the honest refusal.**

This is why `task:delete` only removes the DB row *after* the platform confirms; why an
admin-ACL'd task returns "needs elevation" instead of a fake success; why lossy schedule
conversion surfaces a warning instead of quietly degrading; and why a declared-but-uncompiled
target offers "copy to set up manually" rather than silently no-op'ing.

## Architecture at a glance

Four long-running processes plus Redis, and an on-demand `mcp-server` your AI host launches.
The **agent always dials out** — the server never connects in.

```
┌─ Frontend ──┐  REST/JWT + Socket.io   ┌─ Backend ──┐   Prisma    ┌──────────┐
│  React 19   │ ──────────────────────► │  Express 5 │ ──────────► │ Postgres │
│  :7373      │                         │  :3000     │             │  :5432   │
└─────────────┘                         └──────┬─────┘             └──────────┘
                                        ▲  ▲   │  HTTP (sha256-verified)
┌─ MCP host ──┐  MCP/  ┌────────────┐   │  │   └──────────────► Registry / Webhooks
│ Claude/Codex│ stdio  │ mcp-server │   │  │
│   Cursor    │ ─────► │ REST+Bearer│ ──┘  │
└─────────────┘        └────────────┘      │ WS + HMAC (outbound only)
                                    ┌──────┴─────┐   COM    ┌──────────────────┐
                                    │ .NET Agent │ ───────► │ Win Task Sched.  │
                                    │ host .exe  │          └──────────────────┘
                                    └────────────┘
```

The agent is a **client, not a server** — it never binds `0.0.0.0`. It can't be
containerized because it needs Task Scheduler COM access, which is why it's a host process
and why it **never hot-reloads** (see Traps).

The **`mcp-server` is a peer of the frontend, not a layer of its own** — another REST client
holding a bearer token. That's the whole design: it owns **no logic**, so every guarantee
(owner scoping, no-shell `exec`, signed agent commands, cron→trigger conversion) stays in the
backend where it's already tested. A tool that needs new behavior needs a **backend route**,
not cleverness in `mcp-server/`.

## The two AI surfaces — don't conflate them

Cronsole has two, with different audiences and lifecycles. Most confusion here starts with
mixing them up:

| | **This skill** (`skills/cronsole/`) | **The MCP server** (`mcp-server/`) |
|:---|:---|:---|
| Audience | An agent **working on** Cronsole's codebase | An agent **using** a running Cronsole |
| Surface | `SKILL.md` + `references/` | the tool surface over MCP/stdio (count: read `mcp-server/src/tools.ts`) |
| Needs | Nothing — it's just text | A running backend + a user JWT |
| Canonical doc | [`skills/README.md`](../README.md) | [`docs/user-guides/guides/MCP_Server_Guide.md`](../../docs/user-guides/guides/MCP_Server_Guide.md) |

A third thing shares the name and is neither: the **dev-tooling MCP servers** in the root
`.mcp.json` (context7, playwright, serper, …) that help you *build* Cronsole. That file holds
**both** — the dev tooling *and* a `cronsole` entry pointing at this repo's own product server.
The `cronsole` entry is the only one needing a backend and a token, so it's the only one that
can fail to start.

**The tools**, each mapping 1:1 onto a backend route — no count here on purpose, it was stuck at
"15" through three expansions to 34 (details, wiring, token minting:
[MCP_Server_Guide.md](../../docs/user-guides/guides/MCP_Server_Guide.md)):

| Tier | Tools |
|:---|:---|
| **Read** | `list_tasks`, `list_templates`, `list_folders`, `get_task_history`, **`export_task`** (two formats: `native` = the platform's own definition, restores *this* task onto *this* platform; **`format: 'template'`** = a portable Registry v1 template that recreates it anywhere, **drops platform settings** so never offer it as a backup, and is the only export that works with the agent offline or on a Claude routine), `convert_schedule`, **`list_platforms`** (the capability matrix — call it before planning anything you are unsure is possible; `unsupported` is a boundary, not a to-do), **`get_task_health`** (`unknown` ≠ `ok`), **`get_diagnostics`** (is *Cronsole* working — ask before `get_task_health`; read-only, repairs nothing), **`list_run_history`** (cross-task; rows are runs *Cronsole performed*, and each carries `runKind`), **`list_platform_runs`** + **`get_run_output`** (runs the **platform** recorded — the other population, never merged with the first: `ExecutionLog` means *Cronsole did this*, so on Gemini, GitHub Actions and Vercel it is empty **by design** and this is where the history is. A live read, so it can fail alone; a platform that publishes none answers as a fact rather than an error. `get_run_output` is **one run per call** — a transcript is ~90KB — and its **step list is the answer**, because a run that finished cleanly having skipped the job reads `completed` either way), **`list_task_archives`** (definitions kept when a native task was deleted; each row's `restorable` carries its **reason**), **`list_claude_routines`**, **`list_task_secrets`** (which secrets a native job references vs. which are stored — **names only**; `unreadable: true` is a third state, never an empty list) |
| **Create** | **`create_task`**, `create_native_task` (HTTP), **`create_native_program_task`** (runs an *existing* program on the backend host — the container on a Dockerized install; named `create_native_script_task` until 2026-08-15), **`create_native_script_task`** (a script body *you* write, run under a fixed-list `interpreter` — nothing needs to be on disk), **`create_native_check_task`** (http / tcp / fileFresh / diskFree assertions), `create_task_from_template` (all take `folder`; `create_task` alone also takes **`createFolder`**, default false — see the folder invariant below), **`import_task`** (a `cronsoleTaskVersion` bundle → a task — pass the file **whole**; **Cronsole-native only**, because a native row *is* the task while a Windows definition is XML on the machine), **`restore_task_archive`** (rebuilds a deleted native task as a **new** task — new id, no archived runs reattached, archive kept). Both ungated: **`delete_task` is gated and undoing one is not**, or the flag protecting you from a bad delete also blocks the fix. **`create_gemini_trigger`** is its own tool rather than a `platform` on `create_task`, because the unit of work there is a **prompt** and none of that tool's command/tokenization guidance applies — and because it is the one create that makes an **autonomous agent**, so the three prompt rules ride in its description: never offer a choice (a question stalls forever unattended), always demand explicit failure reporting, grant only the tools the task needs. MCP servers go **by preset name**, so no bearer token ever enters a tool call — which is why this tool waited for presets to exist. A trigger is **immutable in place**, so the tool says create-then-delete rather than implying an edit — and names the UI's **Recreate with changes**, which is the one path that changes a prompt or schedule *without* producing a new task. Rotation stays UI-only on purpose (it takes credential values). |
| **Act** | `run_task` |
| **Modify** (reversible) | `set_task_status`, `update_task_schedule`, `update_task_action` (Windows), **`update_native_job`** (Cronsole-native job spec — **replaces**, never merges, since the two job types share no fields), **`rename_task`** (a Cronsole label only — the platform is untouched, `externalId` unchanged; survives sync), **`untrack_task`** (removes the task from Cronsole, **leaves the platform entry running**; refuses `TASKHUB_NATIVE` **and `CLAUDE_CODE`**, whose rows *are* the task), **`sync_tasks`** (omit `categories` = refresh, adds nothing new; passing them = import, and that also forgets prior untracks inside them) |
| **Create / connect** (Claude) | **`create_claude_routine`** makes a real routine (name · prompt · UTC cron · optional repos/tools) — it needs a readable Claude Code session on the backend's machine, so **check `list_claude_routines` → `session.mode` first** (`oauth` = available, `declared` = tell the user to run `/login`, or create at claude.ai and connect). **`connect_claude_routine`** / **`edit_claude_routine`** / **`disconnect_claude_routine`** remain for the declared path. Connect takes a **live credential as a parameter**, so it lands in the host transcript; prefer the UI when a human is present. Re-connecting an id **replaces** the token (that is the rotation path), while **`edit_claude_routine` keeps it** — fixing a mistyped id must not cost a credential, since claude.ai shows a token once; the tracked task follows the id so its history and star survive. Disconnect is not a delete: the routine keeps running at claude.ai, and the discarded token cannot be recovered. **There is no `delete_claude_routine` and cannot be** — neither Claude API exposes a DELETE (verified by enumerating the surface). Park a routine with `set_task_status`; removing it happens at claude.ai. *(The "deliberately no `create_claude_routine`" note that stood here until 2026-08-13 was true of the documented API and false of the product — see [#50](../../docs/troubleshooting/README.md#50-two-claude-routines-apis-and-the-documented-one-is-the-smaller-one).)* |
| **Destroy** (gated, and **native-only**) | `delete_task` → **`DELETE /api/tasks/:id/native`**, not `DELETE /api/tasks/:id`. Refuses every platform but `TASKHUB_NATIVE` with a **400**, Windows included — so **no MCP verb can destroy an artifact on the machine**; Windows removal over MCP is `untrack_task`. The backend **archives the definition + last 20 runs before deleting** and **refuses the delete if the archive write fails** (task left unchanged); read them back with **`list_task_archives`** and rebuild with **`restore_task_archive`** (`GET`/`POST /api/tools/task-archives[/:id][/restore]`). Until 2026-08-17 nothing could read that archive at all — see [#65](../../docs/troubleshooting/README.md#65-an-exported-task-file-has-nowhere-to-go--and-restore-refuses-it). Registered **only** when `CRONSOLE_MCP_ALLOW_DESTRUCTIVE=true`; otherwise **absent from `tools/list`**, not present-and-erroring. |
| **REST-only** (no MCP tool) | bulk export `POST /api/tools/export/tasks` (`scope: all \| folder \| selection`), **restore `POST /api/tools/restore/tasks`**, the three bulk verbs — **enable/disable `POST /api/tools/tasks/status`**, **recategorize `POST /api/tools/tasks/category`**, **untrack `POST /api/tools/tasks/untrack`** — **analytics `GET /api/tools/analytics`**, **favorites `POST` / `DELETE /api/tasks/:id/favorite`** (the `isFavorite` flag rides on `GET /api/tasks`; `compactTask` does not forward it, so `list_tasks` cannot see stars), **calendar occurrences `GET /api/tools/occurrences`** (`?from&to&includeSystem&maxPerTask` — walks the stored UTC cron over a window and takes **no timezone**; returns per-task instants plus an `unplaceable` list carrying each refusal's reason), connect-pack downloads `GET /api/tools/downloads[/:id]`, plus template import/export, save-as-template, pairing. *(Task import is **not** on this list any more — `import_task` shipped 2026-08-17.)* **The bulk verbs are omitted on purpose, not pending**: friction has to scale with blast radius, and the UI earns that with a typed confirmation past 25 tasks (`TYPE_TO_CONFIRM_THRESHOLD`). An MCP tool has no such gesture, so a bulk untrack of 254 tasks would arrive with less deliberation than the single-task path — the gap the Mass Actions console exists to close. |

**One absence is a decision, not a gap: no MCP tool writes a secret value** (ADR 0003). A native
job refers to a credential as `${secret.NAME}`; the tools can create that reference, and
`list_task_secrets` reports what is still unset, but the value is entered in the app. A tool call
passes through the model's context into the host's transcript, which is precisely where a value
encrypted at rest must not land — the same "friction scales with blast radius" argument that omits
the bulk verbs.

**The gating is tiered, and the tiering is the point** (decided 2026-07-15). Irreversible is
gated; reversible is not. `set_task_status` ships ungated *on purpose*: it is the honest way to
park a task, and gating it would push you toward cronning a task into silence — which is trap
#14 exactly. **A gate that makes the safe path harder than the unsafe one is worse than no gate.**
The gate is an **env var, not a `confirm: true` param**, because a param is filled in by the
model — the caller assuring itself it's sure, which is the missing deliberation, not a substitute
for it. `untrack_task` (2026-07-28) is the same argument applied to *removal*: gating deletion is
only honest once a **safe** way to remove a task from the dashboard exists ungated — otherwise an
agent asked to "clean this up" has one tool for the job and it's the irreversible one.

**Still REST-only:** template import/export, save-as-template, sync, agent pairing, **favorites**
(`POST` / `DELETE /api/tasks/:id/favorite`). If a user asks for one over MCP, say the tool doesn't
exist and offer the REST call or the UI — **never improvise a substitute.**

**Creating a task on a real machine? Read
[references/task-authoring.md](references/task-authoring.md) first** — the creation paths,
command recipes per kind of work (script / exe / shell opt-in / HTTP / CLI agent), the
quoting and folder rules, and how to verify a task actually ran.

## Non-negotiable invariants

Violating any of these is a bug even if every test passes. Most are load-bearing for either
security or honesty.

| Invariant | Why it exists |
|:---|:---|
| **A launcher task is not the process it launched, and one script owns a task name** | Every `\Cronsole-Stack\` task runs `wscript.exe` → `run-hidden.vbs`, which is fire-and-forget, so the instance ends in under a second while what it started runs on unparented. `Stop-ScheduledTask` stops **nothing**, and `LastTaskResult: 0` describes the shim, never the stack — ask `cronsole.ps1 status`. Restarting is a property of the **script** (`cronsole.ps1 restart`, on-demand elevated as `CronsoleRestart`), and **`up` may never be used as a restart**: it is idempotent by design, which is the same property that lets the 5-minute self-heal exist at all. A task’s **name and description are not its definition** — `CronsoleAgent` was registered by two scripts with incompatible actions, `-Force` overwrote as documented, and the docs prescribed a bounce that returned success while changing nothing. Read the registered **action**. Corollary: **every layer needs a keeper that runs as often as the failure can happen** — the Docker engine was started only at logon, so `up` starts it now. ([#86](../../docs/troubleshooting/README.md#86-stop-scheduledtask-on-a-launcher-task-reports-success-and-stops-nothing)) |
| **All schedules stored as 5-field cron in UTC** | Storing local time is a whole bug class (wrong-time runs, DST drift). This is the storage, REST, signed-command and MCP contract — **it does not move**. |
| **A `VITE_*` variable is public by construction — never put a secret in one** | Vite loads `.env.local` in **every** mode (not just dev) and inlines each `VITE_*` reference as a **literal** at build time. `VITE_DEV_TOKEN` therefore compiled a valid owner JWT (`exp` 2036) into `dist/assets/*.js`, and since `getAuthToken()` falls back to it whenever nobody is logged in, **every built copy of the dashboard arrived already authenticated** — the login screen only rendered in a case that could no longer happen. The prefix means *"safe to publish"*, not *"available to the frontend"*. Gate any dev-only fallback on `import.meta.env.DEV` (statically `false` in a build, so the string folds away); `frontend/scripts/check-bundle-secrets.mjs` fails the build if a credential-shaped literal reappears. **The guard reads `dist/`, not the source, on purpose — the source never contained the secret, the compiler added it.** ([#55](../../docs/troubleshooting/README.md#55-the-dashboard-is-already-signed-in-on-a-browser-that-never-logged-in)) |
| **A tracked `.env*` file is an allowlist, not a habit** | `.gitignore` denies `.env*` and re-includes three `.env.example` files plus **`frontend/.env.remote`**, which is a genuine build input (`vite build --mode remote`) holding one public routing value — so untracking it is the wrong fix and would leave the real hazard untouched. The hazard is that a file git already carries **looks** like a secret store, and a token added to one is a one-line diff in a months-old file that nothing would redden. `scripts/check-tracked-env.mjs` (CI `repo-hygiene`) refuses any unlisted tracked `.env*` path, **pins `.env.remote` to `VITE_API_URL=same-origin` and nothing else**, requires example values to be placeholders, and scans every tracked env file for credentials. Patterns have **one definition** (`scripts/secret-patterns.mjs`), shared with `check-bundle-secrets.mjs` — different populations, same fact, so adding a provider covers both. Flagged by the 2026-08-23 cross-repo audit, which found the class **already realised** one repo over (a live Neon admin connection string in a committed migration write-up). |
| **A signature says who was *signed for*; only the row says who *exists*** | `checkToken` — the one definition the REST middleware and the Socket.IO handshake share — ends with a primary-key read of `User` and returns **that row's** id and email. `req.user` is never assembled from the claims *(2026-08-28, the last P0 item)*. Trusting the payload left a correctly-signed token for a **deleted account** valid for its whole life — up to `never`, which is the credential the MCP server holds — and froze the `email` claim at signing time with nothing able to correct it. Only `id` is read today, which is exactly the shape of thing that stays harmless until something reads the other field. The missing row gets its **own** `403` (*"This account no longer exists"*): told *"invalid or expired"*, a caller goes and tries to log in with credentials that are also gone. A DB that cannot answer is a `503` (the revocation lookup's fail-closed rule), a **revoked API token is refused before** the read, and a signed token with no usable `id` is refused before the query rather than throwing inside it. **The cost is stated, not buried:** one indexed read per authenticated request — precisely the property the `jti`-free browser session was built to avoid, traded on purpose, because an identity nobody re-checks is not an identity. And there is **one door**: `verifyToken`, a synchronous payload-trusting sibling whose doc comment still claimed the Socket.IO channel used it (it had moved to `checkToken` with revocation; only its own test still called it), was **deleted** in the same change — a cheap second definition of the thing you just stopped doing is what the next caller finds first. |
| **Remote access is single-origin, loopback-bound, and gated at the network layer** | Cronsole stays local-first; `proxy/Caddyfile` + the opt-in `proxy` / `remote` Compose profiles serve the **built** dashboard at `/` and forward `/api` + `/socket.io`. Three rules: `same-origin` (via `npm run build:remote`) is a **build-time** value that `setApiOrigin` refuses to *store*, since a saved value resolving against the page freezes whichever address it was saved at; `TRUST_PROXY` is **off by default**, and its test is not *"is there a proxy"* but *"can the caller also reach `:3000`"* — **set** on Cloudflare Tunnel (only `proxy:80` is routed, so the proxy is the only way in; without it the login limiter collapses to one global bucket) and **unset on Tailscale** (the tailnet exposes the whole machine, so the header is forgeable). The same proxy yields opposite answers on the two paths. And the proxy binds `127.0.0.1:8080` — cloudflared reaches it over the compose network, and Tailscale reaches it via `tailscale serve --bg --http=8080 http://127.0.0.1:8080`, which re-serves loopback on the tailnet only; binding `0.0.0.0` would publish the dashboard to whatever Wi‑Fi you are on. *(Use the explicit `--http=`: the shorter `tailscale serve --bg 8080` implies TLS and **hangs forever** provisioning a cert when the tailnet has HTTPS off, with no error — `"CertDomains": null` is the tell.)* Cronsole's own login is the **second** factor behind the network gate, never the gate. *(`tailscale serve` publishes to the tailnet; `tailscale funnel` publishes to the **public internet** — never funnel this.)* |
| **The user's timezone lives at the browser's edge and nowhere else** | Cron *fields* read and accept `settings.timezone` (an IANA id, default **`America/Los_Angeles`**); `useScheduleZone().toUtc()` runs **once, on submit**. A zone that reached storage would fork the meaning of every cron in the DB by author, and `create_task` has no access to a browser preference — so the machine surface stays unambiguously UTC and only the human surface converts. Every shifted field prints the stored UTC form beside it. Two refusals rather than guesses: a date-pinned cron whose shift crosses midnight (`0 4 1 1 *` → 31 Dec in Pacific) is unexpressible and stays UTC with a reason; and **DST is asymmetric** — Windows holds its local wall-clock across a transition, a Cronsole-native task does not, and the UI names that. `describeCron` and `/tasks/preview` both take the **UTC** form. **The picker in front of the field changes none of this** (`components/ScheduleBuilder.tsx` + `utils/scheduleBuilder.ts`, 2026-08-18): five shapes (minutes · hours · daily · weekly · monthly) that **compile to a cron string and stop** — nothing downstream can tell an assembled expression from a typed one. Three rules it depends on: it **emits only on interaction** (the round trip is not byte-identical — `0 9 * * 1-5` → `0 9 * * 1,2,3,4,5` — so writing on mount rewrites every task merely opened); it goes **unavailable, never approximate**, for an expression with no picker form; and it **judges no platform's fidelity** — that is `/tasks/preview`, which matters because a shape the picker offers may still convert imperfectly — though **monthly stopped being that example on 2026-09-08**, when the Windows agent gained a real `Monthly` trigger (`0 9 1,15 * *` is now exact; a *specific month* still hits the hourly fallback, and a monthly time that lands on a different local calendar day is refused by the agent rather than approximated — a weekday can be rolled because a week is always seven days, a day-of-month cannot because a month is not). **The calendar view obeys the same edge rule from the other side** (2026-08-26): `GET /api/tools/occurrences` walks the stored cron in UTC and takes **no timezone parameter** — instants in, instants out — because *which calendar day an instant lands on* is a question about the reader, and `utils/calendar.ts` answers it with the same `dayKeyIn` that decides "due today". A second conversion in the stack is how a calendar comes to disagree with the times printed on its own cards. |
| **Structured `exec` stays no-shell** (`{executable, args[]}`) | The P0 injection guarantee. A shell is opted into **explicitly** (`cmd.exe /c "…"`), never implicit. Implicit shell = arbitrary params become arbitrary code. |
| **A collection's membership is declared; a view's is derived** | `TaskCollection` + `TaskCollectionMember` = `TaskFavorite` made plural and named. A **view stores conditions** and resolves to whatever matches; a **collection stores the tasks**, which is the only way to group four tasks from different platforms that share no filterable property. Per-user join, never a column; keyed on the Task row **with a cascade** (the `TaskFavorite` rule — a membership is about a *tracked* task — deliberately **not** the `TaskExclusion` rule, which must outlive its row). `viewFiltersFrom` **strips `collection`**, and that one is sharper than the other rail dimensions: an id is a **foreign key**, so a view storing one breaks rather than degrades when the collection is deleted. `filtersEqual` / `activeFilterCount` exclude it **by omission** — they list what they compare, so a new *drawer* filter must be added there and a new *rail* dimension must not. Every rail node resets the whole rail scope via one `RAIL_SCOPE_RESET`, and rail counts neutralize `collection` like every other rail dimension. **REST-only, like favorites — no MCP tool.** **A pinned folder is NOT one of these**: it is derived, so it is a `RailPin` in `useSettings` (`utils/railPins.ts`) rendered in its **own** rail band beside Collections (one `Band` component draws both, so "same kind of place" cannot drift into a lie) — snapshotting a folder into a collection would freeze a row named after something it stops matching, and resolving membership from a rule would make `TaskCollection` mean two things. A pin stores **no foreign key** (source key + folder name degrade to `0`; a `collectionId` would break), reads its target node's `count`/`patch` instead of re-deriving them, and **outlives its target** — a pin whose folder is gone keeps its row at `0`, or it becomes a row you cannot remove. |
| **A preference follows the account; a fact about the device stays in the browser** | `localStorage` is scoped to an **origin**, so the same install at `localhost:8080` and at a Tailscale name hands one person two stores. Collections and favorites crossed over (rows); rail pins and saved views did not — and both draw the same sidebar, so the gap reads as a bug. The whole `cronsole.settings` blob syncs through **`UserPreference`** (`routes/preferences.ts`): one JSON row per user, `userId` as the primary key so a second row is unrepresentable. **The server stores it and never reads it** — a server-side `Settings` schema would be a second definition of a shape the frontend owns, and its drift is silent (a backend one release behind strips a field a newer browser just wrote). Boundary checks are only *is it an object* and *is it under 64 kB* (under Express's 100 kB default, so our message is the one that fires). **The client hydrates before it may ever push** (`hooks/useSettings.ts`), and a browser holding untouched defaults does **not** seed — otherwise opening the dashboard once on a phone flattens a curated desktop. `data: null` (never stored) and `{}` (stored defaults) are different answers and the client acts on the difference. Conflicts resolve by recency over the **whole document**, never field-by-field. ## Working rules

1. **Start from `docs/ROADMAP.md`.** It's the plan of record. A material decision updates it **first**, then you implement.
2. **Check `docs/troubleshooting/README.md` before debugging** any setup/runtime failure. Most "impossible" behavior is a known trap above.
3. **`context7` before writing** against React, Prisma, Express, Socket.io, Tailwind, .NET, or WiX.
4. **Templates are content, not code.** Never inline them in `seed.ts`. Edit `bundled.ts` → `npm run registry:build` → commit `registry/` → merge to `main`, which publishes it.
5. **Never hand-edit `registry/`.** It's generated and content-addressed. The drift test will fail you.
5a. **Same for the Connect Pack.** Edit the markdown in `backend/src/tools/connect-pack/`, then `npm run connectpack:build` — never `connectPackBundled.ts` directly. It's bundled rather than read from disk because **`tsc` emits only `.js`**, so loose `.md` under `src/` never reaches `dist/`: a filesystem read would work under `tsx` in dev and 404 in production. A drift test fails if the bundle and the markdown disagree.
6. **A material change ships with its test.** A bug fix ships with a test that failed before it.
7. **Four things run stale**: the Dockerized backend, the published agent, `mcp-server/dist/`, and — the newest and quietest — **the container's generated Prisma client** (`node_modules` is a shadowed volume, so a host `prisma generate` never reaches it; the DB and the client then disagree, and a missing enum member becomes a silent partial write, [#22](../../docs/troubleshooting/README.md#22-deleted-a-windows-task-synced-and-cronsole-still-shows-it--while-reporting-missing-n)). When live behavior contradicts source, suspect these before your logic.
8. **Prefer the honest refusal** over the graceful lie. See "The one thing to understand."
9. **The MCP server and this skill are mirror surfaces — update them in the same change.** See below.
9a. **So are the two published surfaces, and they are the only ones a stranger reads.** A catalog
    change needs `npm run registry:build` and the **committed** `registry/`; merging that to `main`
    publishes it (`.github/workflows/publish-registry.yml`, since 2026-08-19), and the daily
    **Registry drift** workflow reddens if publishing ever stops working
    (`node scripts/check-registry-published.mjs` runs it by hand). `pwsh scripts/publish-registry.ps1`
    is the manual path and now **refuses any branch that is not up-to-date `main`** — it mirrors the
    working tree, so a stale branch replaces the public catalog with an older one and still prints
    *"Published."* ([#68](../../docs/troubleshooting/README.md#68-the-hosted-registry-goes-backwards-after-a-successful-publish)).
    **The front door is automated too, as of the same day**: `registry-site/index.html` is one page
    on two hosts (`cronsole.mikesailab.com` and `mikesailab.com/cronsole-registry/`), and merging to
    `main` publishes it to both (`publish-frontdoor.yml` + `publish-registry.yml`), with
    **Front door drift** comparing served sha256 at both daily. The stale half is always whichever
    host you did not happen to open, which is why it is checked rather than eyeballed. Never keep
    manual work in the two publish clones (`Repos/Tools/cronsole-registry`, `Repos/Tools/cronsole-site`)
    — each script `git reset --hard`s them first, and both now refuse a branch that is not
    up-to-date `main`.
    **Be accurate about who a stale registry hurts**: `TEMPLATE_REGISTRY_URL` is commented out by
    default, so a default install reads the compiled-in `bundled.ts` and needs no publish. The hosted
    artifact is what the **public gallery** serves and what an opted-in install syncs — and
    `catalogSync` auto-syncs only `core: true`, so extended templates arrive by being browsed and
    imported.
10. **Commits**: conventional prefix, imperative subject (`feat:`, `fix:`, `docs:`, `chore:`, `refactor:`, `test:`).
11. **Never commit** `.env*`, `node_modules/`, `dist/`, `bin/`, `obj/`, `*.msi`.

## Two skills, two audiences — don't merge them

There are **two** Cronsole skills, and confusing them ships the wrong document to the wrong reader:

| | This skill (`skills/cronsole/`) | The Connect Pack (`backend/src/tools/connect-pack/`) |
|:---|:---|:---|
| **Reader** | Someone working **on** the Cronsole codebase | An end user's AI tool **using** a running Cronsole |
| **Contains** | Architecture, catalog internals, the agent protocol, repo traps, test layers | The tool surface, the invariants, schedule traps, how to verify |
| **Ships via** | The repo, through a per-machine junction | A download in the dashboard's **Tools** tab |
| **May reference** | `catalogSync`, `normalize.ts`, `bundled.ts`, repo-relative links | **None of those** — an audience test fails the build if they leak in |

Distributing *this* skill to end users would hand them registry-publishing internals instead of
usage instructions. When you add a capability, ask which reader needs it — often both, in
different words. The pack is **version-stamped** because a copy on someone else's machine is a
mirror surface you can never update: it can't be kept current, so it must be able to say how old
it is.

## Keeping the mirror surfaces in sync

`mcp-server/` and this skill both **describe** Cronsole rather than implement it, so neither
breaks loudly when it drifts — the tests stay green, and the drift surfaces later as an agent
confidently doing the wrong thing. That's "the confident lie" aimed at your future self.
**They don't get a follow-up pass; they ship in the same change.**

Two asymmetries worth holding onto:

- **The repo wins.** When this skill and a doc disagree, the doc is right — fix the skill.
- **`mcp-server/` holds no logic.** If syncing it tempts you to add behavior there, that
  behavior belongs in a backend route. A wrapper that grows logic stops being a wrapper, and
  the guarantees quietly fork.
