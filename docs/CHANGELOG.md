### Security
- **Production dependency advisories back to zero across all three JS packages** (2026-07-28): the P1 claim below ("production `npm audit` is 0") had **drifted** — new advisories landed against dependencies that were clean when it was written, and nothing re-checks it, so it sat as a stale-but-plausible statement. Re-audited and remediated: backend `axios` 1.16.1 → **1.18.1** and `body-parser` 2.2.2 → **2.3.0** (10 axios advisories incl. prototype pollution and `maxBodyLength` bypasses, plus a body-parser DoS where an invalid `limit` silently disables size enforcement); frontend `axios` likewise; `mcp-server` `fast-uri` and one moderate transitive. **Production `npm audit` is now 0 for backend, frontend, and mcp-server.** All 561 tests green after the bumps (backend 319, frontend 115, mcp-server 127) and all three builds pass.
  - **One advisory is deliberately left open, with reasoning rather than a version bump:** `react-router` 7.12.0–8.2.0 *"RSC Mode CSRF Bypass Allows Action Execution Before 400 Response"* (high). npm's only offered remedy is `--force`, which **downgrades** `react-router-dom` to 7.11.0 and is flagged breaking. The vulnerable path is **React Server Components mode**, and the frontend is a static Vite SPA that uses only `BrowserRouter` / `useNavigate` / `useLocation` — no `createBrowserRouter`, no `RouterProvider`, no loaders or actions, and no server at all. The code path is unreachable, so downgrading a core router (risking the routing + deep-link work) buys nothing. Re-evaluate when a forward fix ships. **Recorded here rather than left as a mysterious non-zero audit** — an unexplained advisory is how the next person learns to ignore the whole report.
- **Security audit + production dependency remediation** (P1 QA final slice): audited REST auth/session/CORS/error handling, agent Socket.IO auth and command signing, structured command execution, stale-pruning safety, frontend storage/XSS-sensitive patterns, native HTTP jobs, and dependency advisories. Remediated high production advisories by updating lockfile transitive packages: backend `engine.io` 6.6.8 -> 6.6.9, `socket.io-adapter` 2.5.7 -> 2.5.8, `ws` 8.20.1 -> 8.21.0, `form-data` 4.0.5 -> 4.0.6; frontend `form-data` 4.0.5 -> 4.0.6. Post-fix production `npm audit` is 0 for backend and frontend; NuGet vulnerability checks are clean for the agent projects. Remaining public-hosting security work is tracked in the Go-public checklist: REST CORS restriction, auth/API rate limiting, Helmet/security headers, real account/session flow, per-user agent pairing, and SSRF guardrails for hosted native HTTP jobs.
- **Agent-auth hardening follow-ups** (P1, closes the three residuals from the 2026-07-09 WebSocket-auth review): (1) **`task:create`'s trigger is now signed** — the per-command HMAC message gained a canonical trigger field (`canonicalizeTrigger` in `backend/src/utils/scheduler-conversion.ts`, mirrored by `AgentAuthenticator.CanonicalizeTrigger` in C#; fixed-order pipe-joined, null → `"none"`), so an on-path attacker on a plaintext link can't rewrite a task's schedule in flight. The agent parses the trigger before verifying and the shared golden vector gained null-trigger + Weekly-trigger create cases. (2) **Per-command replay guard** — the agent rejects a `(ts, sig)` already accepted within the freshness window (bounded, self-pruning cache). (3) **Session-key reconnect overlap** — the agent keeps the current session key (non-expiring) plus any superseded key for a grace window and verifies against either, so a command signed under the old connection isn't false-rejected when the socket rekeys. `emitSignedCommand`'s `extra` param was removed (trigger is a first-class signed field now). **Breaking:** the create signature changed — agent and backend must deploy together. Verified live end-to-end (Windows task with a real Daily trigger created + a signed run >120s after handshake, which caught and fixed a latent "all keys expire after 120s" bug). Backend 121 tests (+3), agent 56 tests (+10).
- **Server-side per-token template substitution** (P1, closes the structured-command residual): the Apply flow used to substitute `{{placeholders}}` into the command string in the browser and send the finished string; the backend then tokenized it, so a parameter value containing an unbalanced quote could split into extra literal arguments. The client now sends **raw parameter values** (`parameters` in `POST /api/templates/:id/apply`) and the backend owns substitution (`backend/src/utils/templateCommand.ts`): the template is tokenized first, then values are substituted per-token — a quoted or composite placeholder (`-File "{{scriptPath}}"`, `--flag={{v}}`) is always exactly **one argument** regardless of quotes/spaces in its value, while a bare placeholder token (`{{args}}`) keeps its intended multi-argument semantics (contained to that position). Parameters are validated server-side against the template's declared definitions (required non-blank, `select` values must match an option, undeclared keys and non-string values rejected with specific 400s). The resolved `{ executable, args[] }` action is passed straight to the agent connector (no re-tokenization of the display string); non-argv platforms (native HTTP jobs) get whole-string substitution. The legacy pre-substituted `command` body field still works (deprecated). Verified end-to-end: a `scriptPath` of `C:\nonexistent\x.ps1" & calc.exe` registers in Windows Task Scheduler as a single backslash-escaped argument to `powershell.exe`. Tests: backend 116 (+23), frontend 45.
- **Structured command handling — no `cmd.exe /c` shell wrap** (P0, completes P0 security): the agent registered every created task as `cmd.exe /c "<command>"`, so a template parameter substituted into the command string was interpreted by the shell — command injection / RCE on the user's machine. The backend now structures the resolved command into `{ executable, args[] }` (`backend/src/utils/commandParser.ts`, a quote-aware tokenizer) and the agent registers a **direct ExecAction with no shell** (`agent/TaskHub.Agent/ArgumentQuoting.cs`, Windows `CommandLineToArgvW` per-arg quoting). With no shell parsing the line, a malicious parameter can at most become a malformed argument to the intended program — it can't launch a second process. The structured action is covered by the `task:create` HMAC signature (a new action-canonical field, executable + args joined by 0x1F, pinned by the shared cross-language golden vector). `ITaskScheduler.CreateTask` now takes an `AgentExecAction`; two Tier-B seed patterns that need a shell (`pg_dump … > backup.sql`, `del /q %temp%\\*`) now name `cmd.exe /c` explicitly. **Breaking:** agent and backend must be deployed together (the create signature changed). Tests: backend 93 (+10), agent 46 (+7).
- **Multi-tenancy route scoping + JWT fail-fast + dev-JWT rotation** (P0): the task API ran as a single hardcoded `cli_user_placeholder`, and its by-id routes looked tasks up by `id` alone — so any authenticated caller could list every user's tasks (`GET /api/tasks` had no owner filter) and read/patch/delete/**run** anyone's task by id (IDOR; the run path is remote command execution on another user's agent). Every task route now derives `userId` from the verified JWT (`req.user.id`) and scopes its queries: `GET /` filters by `userId`; `PATCH`/`DELETE`/`POST /:id/run` use `findFirst({id, userId})` and 404 on a miss; `GET /:id/executions` confirms task ownership before returning logs; create/native/health/sync/discover and the template `apply` route attribute to the token user. The backend now **fails fast on a missing/weak `JWT_SECRET`** (`>= 16` chars; the `|| 'fallback-secret'` default that let anyone forge a token is gone). The **committed dev JWT was removed** from `frontend/src/api.ts` and replaced with an env-sourced `VITE_DEV_TOKEN` (gitignored `.env.local`, no committed fallback), and **`JWT_SECRET` was rotated** — invalidating the leaked token. Added `.env.example` for backend and frontend. Templates remain a shared seeded catalog by design.
- **`PlatformConnection.config` encrypted at rest** (P0): the connection config column — which holds API keys, agent IDs, and pairing secrets — was stored as plaintext JSON, so any DB dump or backup leaked every credential. It's now encrypted with the existing AES-256-GCM helpers, routed through a single new module (`backend/src/auth/connectionConfig.ts`): `serializeConfig()` encrypts on write, `deserializeConfig()` decrypts on read. The Prisma column stays `Json`; the ciphertext is stored as a JSON string (`iv:tag:ciphertext`), and since encrypted configs are strings while legacy configs were objects, the stored type disambiguates the two — **legacy plaintext rows keep working with no migration**. Every config read (create/apply-template/health/sync×2/run across `routes/tasks.ts` + `routes/templates.ts`) and both writes (the native + Windows connection auto-provision) go through the helpers; no route reads `connection.config` directly anymore. Tampered/wrong-key payloads throw (GCM auth failure is surfaced). Importing the module also makes the backend fail fast on a missing/short `ENCRYPTION_KEY` at boot. Tests: +5 `connectionConfig` cases (round-trip, empty, legacy passthrough, null/undefined, tamper rejection) → 83 backend tests.
- **Agent WebSocket authentication** (P0): the agent↔backend Socket.IO channel is no longer unauthenticated. The backend now runs an `io.use()` handshake middleware (`backend/src/ws/agentAuth.ts`) that verifies an HMAC-SHA256 proof over `(agentId, nonce, ts)` against a shared `AGENT_PAIRING_SECRET` (with a 120s freshness window and constant-time compare) and **rejects any socket that can't authenticate** — closing the "any process reaching port 3000 gets remote command execution" gap. The handshake is single-use within its window (server-side nonce replay cache) so a captured handshake can't be replayed to displace the live agent. State-changing commands (`task:run` / `task:create` / `task:set_status`) are signed server-side with a **per-session key** derived from the handshake nonce, and the .NET agent (`AgentAuthenticator.cs`) **refuses to execute any command it can't verify** (bad signature or stale timestamp). Socket.IO CORS is restricted to `ALLOWED_ORIGINS` (empty by default; only the non-browser agent connects today). The agent reads its server URL + pairing secret from env (`TASKHUB_SERVER_URL`, `TASKHUB_PAIRING_SECRET`, `TASKHUB_AGENT_ID`; WSS-capable) **or** a gitignored `agent/TaskHub.Agent/appsettings.json` (env overrides the file; `appsettings.example.json` is the committed template, copied beside the published exe so the Windows auto-start task picks up the secret without re-exporting it), and the backend fails fast if `AGENT_PAIRING_SECRET` is unset/weak. The auto-start / self-heal scheduled task was re-published and validated end-to-end (published agent authenticates from its bundled config; Windows connector reports `HEALTHY`). A shared cross-language HMAC golden vector is asserted by both `backend/src/ws/__tests__/agentAuth.test.ts` and `agent/TaskHub.Agent.Tests/AgentAuthenticatorTests.cs` so the two implementations can't silently diverge. **Breaking:** existing agents must be rebuilt with the pairing secret configured.

### Added
- **Gallery search is global, and packs are now a filter** (registry, 2026-07-28): three changes to the template gallery, plus a latent routing bug they exposed.

  **1. Search moved into the header, on every view.** It previously lived *inside the filter rail* — which is a collapsed drawer on mobile and doesn't exist at all on Home, Collections, or a pack page. So the catalog had search, but only if you were already on Browse and only if you opened the filters. It now sits in the nav on every page, with a **`/` shortcut** to focus it and **Escape** to clear, and typing from any view jumps straight into filtered Browse results. The input deliberately lives **outside `#app`**, because `route()` replaces `#app.innerHTML` on every render — an input inside it loses focus and the caret mid-keystroke.

  **2. Pack is a filter dimension.** Packs shipped earlier the same day but Browse couldn't see them, so the only way to view one was the separate Collections page. There is now a **Pack facet** with cross-faceted counts, active pills, a `#/browse?pack=<id>` deep link, and a **"Filter & search this pack"** button on each pack page that hands off to a filtered Browse. Membership is read from the registry, so there is no second definition of what a pack contains. Selecting two packs is OR within the dimension (in *either*), matching how availability and category already behave.

  **3. The filter rail is itself searchable.** With 40+ tags truncated to 14 behind a "+more", finding the *filter* was its own search problem. A **"Search filters…"** box narrows the options across every facet, hides facets with no match, and reveals all matching tags instead of the truncated set. It is a **separate state field** from the template search — the two do different jobs and neither resets the other.

  **The bug this surfaced:** `#/browse?pack=monitoring` landed on **Home**. `parseHash()` split the raw hash on `/` *before* stripping the query string, so `parts[0]` was `"browse?pack=monitoring"` — matching no view and falling through to the landing page. This was **pre-existing**: the older `?tag=` deep link had the identical defect and nobody noticed, because tag chips navigate to a bare `#/browse` and apply the filter in JS rather than through the URL. Every query-string deep link had been silently 404-ing to Home. Fixed by splitting the path only.

  **Verified in a real browser** on the live registry data: typing in the header search filters live while keeping focus through every keystroke (the failure mode that made the header placement necessary); pack facet counts cross-facet correctly (`docker` → Developer 2, Backup & Cleanup 1, Monitoring 1, rest dimmed); search and pack filter compose (`codex` + AI & Agents = exactly 3); the rail search collapses to just `#git`/`#github` while leaving template results untouched, proving the two searches are independent; the `?pack=` deep link and the pack-page hand-off both land on a correctly filtered Browse; zero console errors. **Honest gap: the mobile layout was not visually verified** — the browser window would not actually resize in this environment (it reported success while `innerWidth` stayed 2124). The narrow-screen rule is reasoned from measured widths (brand + icon buttons consume ~241px of a 375px row, leaving the search ~118px), so below 620px the nav wraps and the search takes its own full-width row. Worth a real device check.
- **Template packs are downloadable — one file, one import** (registry, 2026-07-28): the gallery could only hand you templates **one at a time**. Now every collection has **Download all N**, which serves a pre-built bundle containing the whole pack.

  **Packs became a first-class registry concept rather than a gallery trick.** They previously existed only as JavaScript predicates inside `registry-site/index.html` — `tags.includes('dev')`, `category === 'monitoring'`. That is invisible to the registry, to the app, and to any other consumer, and worse, membership was **derived**: tagging an unrelated template `dev` silently changed what the "Developer Pack" contained. Tolerable while a collection was just a filtered view; **not** tolerable once a pack is a file that lands in someone's catalog.

  So membership is now **declared** in `backend/src/catalog/packs.ts`, and `buildRegistry` **throws** on an unknown or duplicated template id — the failure moves from silent drift to a broken build. `index.json` gained an optional `packs[]`, and the artifact gained `registry/packs/<id>.json`, content-addressed by sha256 exactly like templates.

  Decisions worth keeping:
  - **The bundle is the shape import already accepts.** `{ taskhubCatalogVersion, pack, templates[] }` — `POST /api/templates/import` reads `.templates` and ignores the rest, so downloading a pack is one file and one import, not N downloads and N imports. No backend change was needed at all.
  - **`packs` is optional in both directions**, so it shipped without a coordinated release: a registry published before packs has no key and still parses, and an app built before packs parses a registry that has one (Zod's `z.object()` strips unknown keys rather than rejecting). With no packs declared the key is **omitted entirely**, keeping a pre-packs registry byte-identical.
  - **No timestamp inside a bundle.** Registry files are hashed over exact bytes; a clock in the payload would change the hash every build and make the drift test meaningless.
  - **The browser never assembles the bundle.** It fetches the published file, so what you download is byte-for-byte what the registry published — verifiable against its `sha256`.
  - **A new sixth pack, "System & Utilities"** (8 templates: service restart, DNS flush, update scan, battery + event-log reports, rclone sync, two heartbeats). Without it those eight belonged to **no** pack, so "download every pack" would have been quietly less than the catalog. Coverage is now 55/55, asserted by a test.
  - **The registry owns the data, the gallery owns presentation** — icons/colors are keyed by pack id with a default, so adding a pack needs no site change.

  **Verified end to end against the running stack**, which is the one thing the unit suite structurally cannot do (it can't prove the wrapper and the real route still agree): the file downloaded from the gallery in a real browser is **byte-identical** to the published bundle (12,170 bytes), and posting it **untouched** to `POST /api/templates/import` returned *11 total, 10 created, 1 updated, 0 errors*. The test import was then reverted, restoring the catalog to its original 5 rows. All six collections render from the registry with correct counts (20 / 11 / 11 / 8 / 6 / 8) and zero console errors.

  **Tests:** +9 backend (sha256 matches bytes, bundles importable as-is via the real `extractTemplateCandidates`, every member is a real template, full 55/55 coverage, unknown-id and duplicate-id build failures, packs key omitted when empty, declared order preserved, bundles deterministic across clocks). Mutation-tested — dropping either guard, always emitting the key, or scrambling declared order each fails exactly the assertion that pins it. `publish-registry.ps1` now mirrors `packs/` with the same delete-then-copy semantics, so a removed pack's URL stops working instead of silently serving a stale bundle.
- **A "Tools" tab: bulk task backup, and downloads that connect other AI tools** (P2, 2026-07-28): a fifth tab beside Dashboard / Templates / Platforms / Settings, at `/tools`, holding two utilities that act across tasks rather than on one.

  **1. Back up scheduled tasks.** Export **all** Windows Task Scheduler tasks, or all tasks in **one folder**, as native XML. This closes a real hole: the *Clear all MISSING* feature above exists because one deleted Task Scheduler folder can flag dozens of tasks missing at once — and until now that was an unrecoverable loss. TaskHub could tell you the tasks were gone and clear the rows; it could not give them back. New `POST /api/tools/export/tasks` (`backend/src/services/bulkExport.ts` + `backend/src/routes/tools.ts`).

  **The finding that shaped the work: it needed no agent protocol change.** `task:export` takes a raw `taskPath` and never checked that the path belongs to a *tracked* task — it is read-only and unsigned, like `task:list` — so the agent could already export anything on the machine; the restriction to imported tasks lived entirely in the old route, which is keyed on a DB row. Combined with the existing full enumeration, "export every folder" became backend + frontend work only, with **no agent republish**.

  Decisions worth keeping:
  - **It exports the machine, not the imported subset — and says so.** The tasks most at risk are the ones nothing else is tracking. An "Export all" that quietly meant "all the ones we happen to know about" would be the same invisible fence that made un-imported tasks impossible to notice ([#20](troubleshooting/README.md#20-sync-now-never-brings-in-a-task-you-just-created-in-task-scheduler)).
  - **`\Microsoft\` is excluded by default, and the count is shown rather than hidden.** On the real machine the split is 95 user tasks vs **257** system ones; including them by default would bury the 95 that matter, and dropping them silently would be the opposite failure. A checkbox opts in.
  - **The archive is built server-side, and the base64 path exists for the same reason.** Task Scheduler XML is UTF-16 LE + BOM — the only encoding Windows re-imports — so the bytes never travel as JSON text, which is exactly how the MCP `export_task` tool once decoded UTF-16 as UTF-8 into mojibake.
  - **Destination:** the browser's File System Access API gives a real folder picker (Chromium; `localhost` is a secure context, so it works for a local-first app), with a single-ZIP download fallback elsewhere. The picker opens **before** the export request because it needs transient user activation ([#24](troubleshooting/README.md#24-showdirectorypicker-throws-must-be-handling-a-user-gesture-after-an-await)).
  - **The agent is deliberately NOT given a file-write verb.** It is already on the machine and already elevated, so "let it write where told" is the tempting shortcut — and it would turn a task-scheduler agent into a general elevated arbitrary-file-write primitive reachable from the backend, in exchange for a directory picker.
  - Every export carries a `_taskhub-export.json` manifest naming what was saved, what was skipped, and what failed; one unreadable task is recorded and the run continues, because a backup that saves 94 of 95 and says which one it missed beats one that aborts.

  **2. Connect another AI tool.** Downloads that teach Claude Code, Cursor, Codex, or a custom agent to drive *this* TaskHub: a skill (`SKILL.md` + a task-authoring reference), an `AGENTS.md` system prompt for hosts with no skill concept, an MCP config snippet, and a full pack. New `GET /api/tools/downloads` + `/:id`. **These are newly authored, not the repo's own skill** — `skills/taskhub/` teaches an agent to work *on* the TaskHub codebase, so shipping it to an end user would hand them `catalogSync`, `normalize.ts`, and registry-publishing internals instead of usage instructions. Every artifact is version-stamped and points at a canonical URL, because a downloaded copy on someone else's machine is a mirror surface that can never be updated — it cannot be kept current, so it must at least be able to say how old it is.

  **Verified live against the real agent, with evidence from outside TaskHub.** Full-machine export: 352 enumerated → 95 exported → 0 failed, in 1.7s, 257 system tasks skipped. Every one of the 95 files carries the `FF FE` BOM; the archive mirrors the folder tree across 14 folders with no `Microsoft/` present; a bulk-exported XML is **byte-identical** to the same task from `GET /api/tasks/:id/export` (3,908 bytes, zero differing bytes) on both the ZIP and base64 paths. Decisively, an exported file was fed back through **Windows' own `Schedule.Service` COM parser**, which accepted it and read back the action and trigger — the reporting layer cannot be its own witness, so the proof came from Task Scheduler itself. The tab was then driven in a real browser: live counts (95 / 257), the folder picker populated with real folders and counts, scope switching, and zero console errors.

  **Tests:** 51 backend (bulk-export selection, system exclusion, folder scoping, filename collisions, BOM encoding, bounded concurrency, partial failure, manifest; plus connect-pack assembly, version stamping, and an audience guard asserting no repo internals or repo-relative links leak into the shipped pack) and 27 frontend (byte-fidelity of the directory-write path against a fake handle, count arithmetic, scope switching, ZIP-vs-picker branching, partial-failure reporting). All mutation-tested — dropping the `\Microsoft\` exclusion, the BOM, the collision counter, the folder scoping, or the frontend system filter each fails exactly the assertions that pin them. The connect pack's markdown compiles into a bundled module (`npm run connectpack:build`) guarded by a drift test, because `tsc` emits only `.js` and loose `.md` files would never reach `dist/`. Honest residual: the **native folder picker dialog itself** cannot be driven by automation, so the OS dialog is a manual check — the writing logic behind it is unit-tested against a fake directory handle.
- **The dashboard now says what a sync *didn't* import** (2026-07-27): Sync Now can only refresh folders you already track — it **cannot discover a new one** — and it never said so. A user created tasks in `\IAM\` and `\Edge-Radar-MikesAILab\`, pressed Sync Now repeatedly, and got a cheerful `Tasks synced.` every time while 26 tasks sat one fence away; `/discover` had been reporting them the whole time. Excluding them *silently* would be the opposite failure, so `systemCount` is reported, just not counted. **(2) The message is deliberately not gated behind `toastOnSuccess`** — that setting suppresses routine "it worked" noise, and this is its inverse: the one thing the sync did **not** do, and the only prompt a user gets that Import exists. **Verified end-to-end against the real thing, twice.** First arithmetically, by forcing an empty include-set on the real 352-task machine: 95 user tasks / 13 folders / 257 system, and 95 + 257 = 352 exactly accounts for the enumeration — nothing silently dropped — with the probe mutating nothing (`missing: 0`, DB unchanged). Then **for real**: a new `\Testing-Import\` folder holding one task was created natively in Task Scheduler, reproducing [#20](troubleshooting/README.md#20-sync-now-never-brings-in-a-task-you-just-created-in-task-scheduler) exactly. `/discover` saw it immediately, Sync Now correctly still refused to import it (`count: 352`, unchanged), and the response carried `untracked: {count: 1, folders: ["Testing-Import"]}` — where before it would have returned only `{count: 352, missing: 0}` and the UI would have said `Tasks synced.` The toast was then **observed rendering in a real browser**: *"Synced. 1 task in 1 folder isn't imported — use Import to add it."* — the singular grammar path, character-for-character identical to the unit test that pins it. Tests: 6 backend + 7 frontend (the toast copy, including its plural forms, pinned by extracting `describeUntracked` into a pure helper rather than leaving it inside a mutation callback), all mutation-tested — dropping the system-category split, treating "no filter" as "everything is untracked", emitting the message at zero, and double-counting a folder each fail exactly the assertion that pins them.
- **Clear all MISSING tasks in one action** (2026-07-25): a single sync can flag dozens of tasks `MISSING` at once — deleting a Task Scheduler folder takes every task under it, which is the normal case rather than an edge case — but clearing them was per-task only: 55 modal open → confirm → close cycles. The asymmetry was the defect: the operation that creates the mess in bulk offered no way out in bulk. New `DELETE /api/tasks/missing` plus a **Clear N Missing** button that renders only when N > 0 (a permanent "Clear 0" would be noise on a healthy dashboard), with a danger-toned confirm stating exactly what happens: TaskHub's records and their run history go, **nothing on your machine is touched**, and if a task still exists the next sync re-imports it. Three implementation notes worth carrying: the route is registered **above `DELETE /:id`**, because Express matches in declaration order and the parameterised route would otherwise capture `missing` as a task id and answer 404 — a route that silently never runs; it deliberately makes **no platform call**, unlike the single delete, since `MISSING` means the platform already reported the task gone and there is nothing left to remove or confirm; and the query is **guarded against a stale generated client**, because `TaskStatus.MISSING === undefined` inside a **`where`** clause is *ignored* by Prisma and would silently widen to every task the user owns — the exact inverse of [#22](troubleshooting/README.md#22-deleted-a-windows-task-synced-and-taskhub-still-shows-it--while-reporting-missing-n), which under-wrote a field where this would over-delete rows. 5 integration tests against real Postgres (only-MISSING, owner scoping, log cascade, 0 no-op, and route-order), mutation-tested against both a dropped status filter and a dropped owner scope; the confirm/cancel path verified in a real browser, including that Cancel leaves all 55 rows intact.

- **MCP task management — the surface goes 7 → 14 tools** (P3 *MCP surface expansion*, the management verbs, 2026-07-15): an assistant could create and run tasks but could not **manage** them — it couldn't answer *"did last night's job work?"*, couldn't park a task, couldn't fix a wrong command, and couldn't say what was actually registered. Seven new tools, each wrapping a route that **already existed**, with **no new backend logic**: **`create_native_task`** (`POST /api/tasks/native` — a full HTTP job spec with method/headers/body, distinct from `create_task`'s URL-only native path), **`get_task_history`** (`GET /api/tasks/:id/executions`), **`export_task`** (`GET /api/tasks/:id/export`), **`set_task_status`** (`PATCH …/status`), **`update_task_schedule`** (`PATCH …/schedule`), **`update_task_action`** (`PATCH …/actions`), and **`delete_task`** (`DELETE /api/tasks/:id`, gated — below). The wrappers were the mechanical part; **the gating decision was the actual work**, and it's now settled and recorded in the roadmap.
  - **The gate is tiered, not blanket.** Read-only and *reversible* verbs ship ungated; only the *irreversible* one is gated. **`set_task_status` ungated is a deliberate safety choice**: it is the honest way to park a task, and gating it would push an assistant toward the unsafe workaround of cronning a task into silence — which is [#14](troubleshooting/README.md#14-a-rare-cron-becomes-an-hourly-trigger) exactly. **A gate that makes the safe path harder than the unsafe one is worse than no gate.**
  - **`delete_task` requires `TASKHUB_MCP_ALLOW_DESTRUCTIVE=true`**, and when off it is **absent from `tools/list`** rather than present-and-erroring — a tool the model can see is a tool it will plan around, and a capability that announces itself then refuses burns turns on a door that doesn't exist. Only an exact `true`/`1` opens it; a typo, an empty value, or an unexpanded `${…}` literal all fail **closed** (a false negative costs one missing tool; a false positive hands out a deletion verb nobody granted).
  - **Why an env var and not a `confirm: true` parameter:** the model fills a parameter in itself, so it is the caller assuring *itself* it is sure — precisely the deliberation that's missing when there's no confirm dialog. An env var is **out of band**: the human sets it, and no amount of agent reasoning reaches it. That mirrors the posture the elevated agent already takes toward *its* caller (`\Microsoft\` is refused in the agent as well as the backend, because the agent holds the elevation and cannot trust who's asking).
  - **One tool per verb, not mode-flagged mega-tools.** Collapsing the three `update_*` would save two tools and cost the thing that makes them safe: a mode-flagged tool needs one description covering every mode, diluting the per-verb warnings exactly where they matter. **The descriptions are the safety mechanism** — an assistant reads those, not the roadmap.
  - **Honesty carried into the tool text, not just the code.** `get_task_history` says an empty history means *"TaskHub has no record"*, **not** *"it never ran"* — a Windows task firing on its own trigger is recorded by Windows — and warns that a `SUCCESS` is exactly what a hung task reports ([#12](troubleshooting/README.md#12-a-template-passes-every-test-and-still-hangs-on-the-target)). `export_task` decodes the route's **UTF-16 LE + BOM** XML to real text (a plain read would hand back mojibake) and tells the caller it must be *saved back* as UTF-16 or Windows rejects it. `update_task_action` says it **replaces** rather than patches the action.

### Changed
- **The frontend moved off Vite's default port: `5173` → `7373`** (2026-07-27). `5173` is the default every Vite project on a machine wants, so whichever starts first wins and the loser either fails or silently lands on `5174` — leaving `ALLOWED_ORIGINS` pointing at an origin nobody is serving. `7373` is distinctive, and `server.strictPort: true` now makes a collision **fail loudly instead of drifting to the next free port**, because a silently-shifted port is exactly what breaks the live-update socket in a way that looks like a backend problem. ### Fixed
- **The backend no longer dies permanently when it boots faster than Postgres** (2026-07-27): reported as "TaskHub is giving me a network error". The stack looked healthy — all four containers `Up`, port 3000 mapped — but every request returned `HTTP 000` and the log ended with `prisma.user.upsert()` → `FATAL: the database system is starting up`. **Cause: a boot-order race, not a code bug.** `depends_on: [db]` waits only for the DB *container to start*, never for Postgres to *accept connections*; after an unclean shutdown Postgres spends several seconds in crash recovery (`database system was not properly shut down; automatic recovery in progress`) refusing every query, and the boot seed runs straight into it, so `main()` throws before the HTTP server binds. **What made it permanent rather than transient is the supervisor: `tsx watch` survives the crash**, so the container never exits, `restart: unless-stopped` sees a healthy container and never fires, and Docker's port proxy holds `:3000` with nothing behind it indefinitely ([#3](troubleshooting/README.md#3-port-listening-but-http-000--eaddrinuse)). ### Fixed
- **Weekly schedules crossing midnight in UTC showed the wrong day** (found by the live schedule-normalization smoke test): the agent's `TriggerReader` converted a weekly trigger's start *time* to UTC but read its *day-of-week* without the same roll, so a late-evening local trigger reported the prior day (e.g. `Weekly-Analysis`, Sunday 23:45 PDT = Monday 06:45 UTC, normalized to `45 6 * * 0` instead of `45 6 * * 1` — and contradicted its own Monday next-run time). `TriggerReader` now rolls the day-of-week by the local→UTC day shift (matching the already-correct `TriggerBuilder` create path), via a unit-tested `ShiftDayName` helper. Re-verified end-to-end against a real 282-task sync. Agent tests +6 (52 total).
- **`POST /api/tasks` (clone / custom creation) skipped cron→trigger conversion**: Windows tasks created through it (e.g. the Clone modal) fell into the agent's legacy fallback and ran "daily at now+1h" instead of the requested schedule. The route now validates the cron, converts it like the template-apply path, and rejects unconvertible schedules with a 400.
- **Tasks deleted natively no longer linger in TaskHub**: `POST /api/tasks/sync` now prunes DB tasks (and their execution logs) that are missing from the connector's full task list via `TaskService.removeStaleTasks`. Pruning is based on the pre-filter list, so category selections in the Import modal don't affect it; `TASKHUB_NATIVE` and empty connector lists are guarded. Verified live: 22 stale Windows tasks purged.
- **Agent permanently disconnected after a backend outage**: SocketIOClient gives up after its default 10 reconnect attempts, so any backend restart longer than ~1 minute left the agent silently offline until manually restarted. The agent now exposes `ISocketClient.Connected` and runs a 30s watchdog loop that re-calls `ConnectAsync` whenever disconnected — this also covers the agent starting before the backend at boot. (Do **not** "fix" this with `ReconnectionAttempts = int.MaxValue`: the library's internal delay math overflows and every connect throws.)
- **Startup task killed the agent after 3 days**: `setup-agent-startup.ps1` previously registered `TaskHubAgent` with Task Scheduler's default 72-hour execution time limit, which force-stops the long-running agent (restart-on-failure does not apply to time-limit kills). The task is now registered with no execution time limit.
- **Setup script failed on re-run while the agent was running**: the script now stops the scheduled task and kills any running `TaskHub.Agent` process before publishing, so the locked `.exe` no longer breaks rebuilds.
- **Import modal rendered a blank body when discovery returned nothing** (e.g. agent offline), making "Sync Now" look like a no-op. It now shows an explicit empty state pointing at the likely cause.
- Template apply route ignored the Apply modal's edited cron: the modal sends `schedule` but the route only read `scheduleExpression`. Both keys are now accepted, and non-5-field crons are rejected with a 400.
- GitHub Actions CI checks by:
  - Switching from `npm ci` to `npm install` in frontend and backend jobs to resolve cross-platform native package installation issues.
  - Adding `npx prisma generate` in backend pipeline to build the Prisma Client before testing/compiling.
  - Quoting the numeric `ENCRYPTION_KEY` environment variable in the workflow YAML to prevent scientific notation conversion.
  - Adding a `TaskHub.Agent.slnx` solution file inside the `agent/` folder to allow root-level `.NET` CLI commands to execute successfully.
