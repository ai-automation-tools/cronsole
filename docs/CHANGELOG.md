### Security
- **Security audit + production dependency remediation** (P1 QA final slice): audited REST auth/session/CORS/error handling, agent Socket.IO auth and command signing, structured command execution, stale-pruning safety, frontend storage/XSS-sensitive patterns, native HTTP jobs, and dependency advisories. Remediated high production advisories by updating lockfile transitive packages: backend `engine.io` 6.6.8 -> 6.6.9, `socket.io-adapter` 2.5.7 -> 2.5.8, `ws` 8.20.1 -> 8.21.0, `form-data` 4.0.5 -> 4.0.6; frontend `form-data` 4.0.5 -> 4.0.6. Post-fix production `npm audit` is 0 for backend and frontend; NuGet vulnerability checks are clean for the agent projects. Remaining public-hosting security work is tracked in the Go-public checklist: REST CORS restriction, auth/API rate limiting, Helmet/security headers, real account/session flow, per-user agent pairing, and SSRF guardrails for hosted native HTTP jobs.
- **Agent-auth hardening follow-ups** (P1, closes the three residuals from the 2026-07-09 WebSocket-auth review): (1) **`task:create`'s trigger is now signed** — the per-command HMAC message gained a canonical trigger field (`canonicalizeTrigger` in `backend/src/utils/scheduler-conversion.ts`, mirrored by `AgentAuthenticator.CanonicalizeTrigger` in C#; fixed-order pipe-joined, null → `"none"`), so an on-path attacker on a plaintext link can't rewrite a task's schedule in flight. The agent parses the trigger before verifying and the shared golden vector gained null-trigger + Weekly-trigger create cases. (2) **Per-command replay guard** — the agent rejects a `(ts, sig)` already accepted within the freshness window (bounded, self-pruning cache). (3) **Session-key reconnect overlap** — the agent keeps the current session key (non-expiring) plus any superseded key for a grace window and verifies against either, so a command signed under the old connection isn't false-rejected when the socket rekeys. `emitSignedCommand`'s `extra` param was removed (trigger is a first-class signed field now). **Breaking:** the create signature changed — agent and backend must deploy together. Verified live end-to-end (Windows task with a real Daily trigger created + a signed run >120s after handshake, which caught and fixed a latent "all keys expire after 120s" bug). Backend 121 tests (+3), agent 56 tests (+10).
- **Server-side per-token template substitution** (P1, closes the structured-command residual): the Apply flow used to substitute `{{placeholders}}` into the command string in the browser and send the finished string; the backend then tokenized it, so a parameter value containing an unbalanced quote could split into extra literal arguments. The client now sends **raw parameter values** (`parameters` in `POST /api/templates/:id/apply`) and the backend owns substitution (`backend/src/utils/templateCommand.ts`): the template is tokenized first, then values are substituted per-token — a quoted or composite placeholder (`-File "{{scriptPath}}"`, `--flag={{v}}`) is always exactly **one argument** regardless of quotes/spaces in its value, while a bare placeholder token (`{{args}}`) keeps its intended multi-argument semantics (contained to that position). Parameters are validated server-side against the template's declared definitions (required non-blank, `select` values must match an option, undeclared keys and non-string values rejected with specific 400s). The resolved `{ executable, args[] }` action is passed straight to the agent connector (no re-tokenization of the display string); non-argv platforms (native HTTP jobs) get whole-string substitution. The legacy pre-substituted `command` body field still works (deprecated). Verified end-to-end: a `scriptPath` of `C:\nonexistent\x.ps1" & calc.exe` registers in Windows Task Scheduler as a single backslash-escaped argument to `powershell.exe`. Tests: backend 116 (+23), frontend 45.
- **Structured command handling — no `cmd.exe /c` shell wrap** (P0, completes P0 security): the agent registered every created task as `cmd.exe /c "<command>"`, so a template parameter substituted into the command string was interpreted by the shell — command injection / RCE on the user's machine. The backend now structures the resolved command into `{ executable, args[] }` (`backend/src/utils/commandParser.ts`, a quote-aware tokenizer) and the agent registers a **direct ExecAction with no shell** (`agent/TaskHub.Agent/ArgumentQuoting.cs`, Windows `CommandLineToArgvW` per-arg quoting). With no shell parsing the line, a malicious parameter can at most become a malformed argument to the intended program — it can't launch a second process. The structured action is covered by the `task:create` HMAC signature (a new action-canonical field, executable + args joined by 0x1F, pinned by the shared cross-language golden vector). `ITaskScheduler.CreateTask` now takes an `AgentExecAction`; two Tier-B seed patterns that need a shell (`pg_dump … > backup.sql`, `del /q %temp%\\*`) now name `cmd.exe /c` explicitly. **Breaking:** agent and backend must be deployed together (the create signature changed). Tests: backend 93 (+10), agent 46 (+7).
- **Multi-tenancy route scoping + JWT fail-fast + dev-JWT rotation** (P0): the task API ran as a single hardcoded `cli_user_placeholder`, and its by-id routes looked tasks up by `id` alone — so any authenticated caller could list every user's tasks (`GET /api/tasks` had no owner filter) and read/patch/delete/**run** anyone's task by id (IDOR; the run path is remote command execution on another user's agent). Every task route now derives `userId` from the verified JWT (`req.user.id`) and scopes its queries: `GET /` filters by `userId`; `PATCH`/`DELETE`/`POST /:id/run` use `findFirst({id, userId})` and 404 on a miss; `GET /:id/executions` confirms task ownership before returning logs; create/native/health/sync/discover and the template `apply` route attribute to the token user. The backend now **fails fast on a missing/weak `JWT_SECRET`** (`>= 16` chars; the `|| 'fallback-secret'` default that let anyone forge a token is gone). The **committed dev JWT was removed** from `frontend/src/api.ts` and replaced with an env-sourced `VITE_DEV_TOKEN` (gitignored `.env.local`, no committed fallback), and **`JWT_SECRET` was rotated** — invalidating the leaked token. Added `.env.example` for backend and frontend. Templates remain a shared seeded catalog by design.
- **`PlatformConnection.config` encrypted at rest** (P0): the connection config column — which holds API keys, agent IDs, and pairing secrets — was stored as plaintext JSON, so any DB dump or backup leaked every credential. It's now encrypted with the existing AES-256-GCM helpers, routed through a single new module (`backend/src/auth/connectionConfig.ts`): `serializeConfig()` encrypts on write, `deserializeConfig()` decrypts on read. The Prisma column stays `Json`; the ciphertext is stored as a JSON string (`iv:tag:ciphertext`), and since encrypted configs are strings while legacy configs were objects, the stored type disambiguates the two — **legacy plaintext rows keep working with no migration**. Every config read (create/apply-template/health/sync×2/run across `routes/tasks.ts` + `routes/templates.ts`) and both writes (the native + Windows connection auto-provision) go through the helpers; no route reads `connection.config` directly anymore. Tampered/wrong-key payloads throw (GCM auth failure is surfaced). Importing the module also makes the backend fail fast on a missing/short `ENCRYPTION_KEY` at boot. Tests: +5 `connectionConfig` cases (round-trip, empty, legacy passthrough, null/undefined, tamper rejection) → 83 backend tests.
- **Agent WebSocket authentication** (P0): the agent↔backend Socket.IO channel is no longer unauthenticated. The backend now runs an `io.use()` handshake middleware (`backend/src/ws/agentAuth.ts`) that verifies an HMAC-SHA256 proof over `(agentId, nonce, ts)` against a shared `AGENT_PAIRING_SECRET` (with a 120s freshness window and constant-time compare) and **rejects any socket that can't authenticate** — closing the "any process reaching port 3000 gets remote command execution" gap. The handshake is single-use within its window (server-side nonce replay cache) so a captured handshake can't be replayed to displace the live agent. State-changing commands (`task:run` / `task:create` / `task:set_status`) are signed server-side with a **per-session key** derived from the handshake nonce, and the .NET agent (`AgentAuthenticator.cs`) **refuses to execute any command it can't verify** (bad signature or stale timestamp). Socket.IO CORS is restricted to `ALLOWED_ORIGINS` (empty by default; only the non-browser agent connects today). The agent reads its server URL + pairing secret from env (`TASKHUB_SERVER_URL`, `TASKHUB_PAIRING_SECRET`, `TASKHUB_AGENT_ID`; WSS-capable) **or** a gitignored `agent/TaskHub.Agent/appsettings.json` (env overrides the file; `appsettings.example.json` is the committed template, copied beside the published exe so the Windows auto-start task picks up the secret without re-exporting it), and the backend fails fast if `AGENT_PAIRING_SECRET` is unset/weak. The auto-start / self-heal scheduled task was re-published and validated end-to-end (published agent authenticates from its bundled config; Windows connector reports `HEALTHY`). A shared cross-language HMAC golden vector is asserted by both `backend/src/ws/__tests__/agentAuth.test.ts` and `agent/TaskHub.Agent.Tests/AgentAuthenticatorTests.cs` so the two implementations can't silently diverge. **Breaking:** existing agents must be rebuilt with the pairing secret configured.

New [`scripts/Republish-Agent.ps1`](../scripts/Republish-Agent.ps1) (stop → publish → relaunch, refuses honestly when unelevated, logs to `%TEMP%\taskhub-republish.log`, and warns if the dll timestamp didn't advance) plus [`scripts/startup-task/Register-RepublishTask.ps1`](../scripts/startup-task/Register-RepublishTask.ps1), which registers a **no-trigger** `\Task-Hub\TaskHubRepublish` task at RunLevel Highest. Register once elevated; afterwards `Start-ScheduledTask -TaskPath '\Task-Hub\' -TaskName 'TaskHubRepublish'` works from any prompt. **Dev tool** — not registered by `Register-TaskHubStack.ps1` or any installer. Honest about the tradeoff: it is by construction a way to run code elevated without a UAC prompt, but it runs one fixed script from this repo and `\Task-Hub\TaskHubStack` already runs `taskhub.ps1` elevated on a recurring trigger, so it adds an entry point rather than a capability.
- **Windows folder selector on apply** (P2, 2026-07-14): a created Windows task always landed in `\TaskHub\` — the agent hardcoded the folder and both create paths built `externalId` as `\TaskHub\<name>`. That contradicted the rest of the code: `TaskService.extractCategory` already derives a Windows task's category from its **real root folder**, so an *imported* task categorized as `Microsoft`/`Work`/whatever it actually lived under, while every *created* task categorized as `TaskHub` forever. For Windows, **category is a projection of the folder** — so the Apply modal now selects a real one (sourced from a new read-only `task:folders` agent enumeration), and non-Windows platforms keep the local category concept. **Only folders that already exist are offered**, and the agent refuses a create into a missing one: TaskHub creates exactly one folder — its own `\TaskHub`, the same one it prunes when emptied — because deleting a folder needs elevation, so anything else it created would be permanent litter only the user could clear. Never create what you cannot remove. New `folder` param on `POST /api/tasks` and `POST /api/templates/:id/apply`, a new `GET /api/tasks/folders` route, and a `folder` argument on the MCP `create_task_from_template` tool.
  - **`\Microsoft\` and its descendants are refused** (case-insensitively, by root *segment* not prefix — `\MicrosoftEdgeBackups` and `\Work\Microsoft` stay allowed), as is `..` traversal. This is not cosmetic: `RegisterTaskDefinition` **silently overwrites** a same-named task in the same folder and the agent runs **elevated**, so a free-text folder would let the dashboard — or an AI through the MCP tool — destroy a real system task with no error.
  - **The refusal is duplicated in the agent** (`TaskFolderPath.cs`), not only the backend (`windowsTaskFolder.ts`). The agent holds the elevation and calls the overwriting API; a signed command proves *origin*, not *correctness*, so it must not trust its caller.
  - **`folder` is part of the `task:create` HMAC signature**, matching the existing invariant that every field the agent acts on is signed — an unsigned folder would let an on-path attacker redirect a create onto an existing task. Both golden-vector suites were regenerated in lockstep. **Requires an agent republish**; an old agent verifies the old message shape and refuses the create, which fails honestly rather than misplacing a task.
  - Prune-on-delete stays scoped to `\TaskHub\` — empty non-TaskHub folders are the user's to keep.

### Fixed
- **Multi-day weekly schedules no longer silently collapse to one day** (P1, 2026-07-14, found while validating the MCP server): `convertCronToWindowsTrigger` ran `parseInt` over the whole day-of-week field, and `parseInt('1-5')` is `1` — so `0 9 * * 1-5` ("every weekday") became a **Monday-only** trigger reported at **confidence 1.0 with no warnings**, as did any list (`1,3,5`) or range. A confident lie in the layer whose entire job is honest schedules. The same truncation ran in **all three layers**: the reverse path (`convertWindowsTriggerToCron`) kept `daysOfWeek[0]`, so a real Mon/Wed/Fri Windows task **imported** as Mondays-only; and the agent's `TriggerBuilder` resolved only `DaysOfWeek[0]`, so it would have **registered** Monday-only even once the server sent all five. Fixed in all three with a real day parser (lists, ranges, `0`/`7` → one Sunday, unparseable → warned fallback rather than a guessed day), plus a lossy-conversion warning for minute/hour steps that don't divide 60/24 evenly (`*/7` now scores 0.7 and says why; `*/15` still 1.0). 9 new tests (6 TS + 3 C#), each confirmed failing before the fix. ### Fixed
- **Weekly schedules crossing midnight in UTC showed the wrong day** (found by the live schedule-normalization smoke test): the agent's `TriggerReader` converted a weekly trigger's start *time* to UTC but read its *day-of-week* without the same roll, so a late-evening local trigger reported the prior day (e.g. `Weekly-Analysis`, Sunday 23:45 PDT = Monday 06:45 UTC, normalized to `45 6 * * 0` instead of `45 6 * * 1` — and contradicted its own Monday next-run time). `TriggerReader` now rolls the day-of-week by the local→UTC day shift (matching the already-correct `TriggerBuilder` create path), via a unit-tested `ShiftDayName` helper. Re-verified end-to-end against a real 282-task sync. Agent tests +6 (52 total).
- **`POST /api/tasks` (clone / custom creation) skipped cron→trigger conversion**: Windows tasks created through it (e.g. the Clone modal) fell into the agent's legacy fallback and ran "daily at now+1h" instead of the requested schedule. The route now validates the cron, converts it like the template-apply path, and rejects unconvertible schedules with a 400.
- **Tasks deleted natively no longer linger in TaskHub**: `POST /api/tasks/sync` now prunes DB tasks (and their execution logs) that are missing from the connector's full task list via `TaskService.removeStaleTasks`. Pruning is based on the pre-filter list, so category selections in the Import modal don't affect it; `TASKHUB_NATIVE` and empty connector lists are guarded. Verified live: 22 stale Windows tasks purged.
- **Agent permanently disconnected after a backend outage**: SocketIOClient gives up after its default 10 reconnect attempts, so any backend restart longer than ~1 minute left the agent silently offline until manually restarted. The agent now exposes `ISocketClient.Connected` and runs a 30s watchdog loop that re-calls `ConnectAsync` whenever disconnected — this also covers the agent starting before the backend at boot. (Do **not** "fix" this with `ReconnectionAttempts = int.MaxValue`: the library's internal delay math overflows and every connect throws.)
- **Startup task killed the agent after 3 days**: `setup-agent-startup.ps1` previously registered `TaskHubAgent` with Task Scheduler's default 72-hour execution time limit, which force-stops the long-running agent (restart-on-failure does not apply to time-limit kills). The task is now registered with no execution time limit.
- **Setup script failed on re-run while the agent was running**: the script now stops the scheduled task and kills any running `TaskHub.Agent` process before publishing, so the locked `.exe` no longer breaks rebuilds.
- **Import modal rendered a blank body when discovery returned nothing** (e.g. agent offline), making "Sync Now" look like a no-op. It now shows an explicit empty state pointing at the likely cause.
- Template apply route ignored the Apply modal's edited cron: the modal sends `schedule` but the route only read `scheduleExpression`. Both keys are now accepted, and non-5-field crons are rejected with a 400.
- GitHub Actions CI checks by:
  - Switching from `npm ci` to `npm install` in frontend and backend jobs to resolve cross-platform native package installation issues.
  - Adding `npx prisma generate` in backend pipeline to build the Prisma Client before testing/compiling.
  - Quoting the numeric `ENCRYPTION_KEY` environment variable in the workflow YAML to prevent scientific notation conversion.
  - Adding a `TaskHub.Agent.slnx` solution file inside the `agent/` folder to allow root-level `.NET` CLI commands to execute successfully.
