### Security hardening (July 2026)

- **Structured command handling — no more `cmd.exe /c` shell wrap** (fourth P0 blocker done → **P0 security complete**): the agent registered every created task as `new ExecAction("cmd.exe", "/c " + command, null)` — the whole command string ran through a shell, so a template parameter substituted into it (e.g. a `{{scriptPath}}` of `x.ps1 & calc.exe`) was interpreted by cmd = command injection / RCE on the user's machine. Now the backend structures the resolved command into `{ executable, args[] }` server-side (`utils/commandParser.ts`, a quote-aware tokenizer) and the agent registers a **direct ExecAction** — no shell — quoting each argument by Windows `CommandLineToArgvW` rules (`ArgumentQuoting.cs`). Because no shell parses the line, a malicious parameter can at worst become a malformed argument to the *intended* executable; it can never launch a second process. The structured action is **covered by the task:create HMAC signature**: the signed message gained an action-canonical field (executable + args joined by 0x1F), computed identically on both sides and pinned by the shared cross-language golden vector (backend Vitest + agent xUnit both assert the new `createSig`). The `ITaskScheduler.CreateTask` contract now takes an `AgentExecAction` instead of a command string; commands that genuinely need shell features name the shell explicitly (two Tier-B seed patterns updated: `pg_dump … > backup.sql` and `del /q %temp%\\*` now use `cmd.exe /c "…"`). **Breaking** — agent + backend must be deployed together (the create signature changed). Verified: backend 93 tests (+10: `commandParser` + updated vectors), agent 46 tests (+7: `ArgumentQuoting` + updated create/vector tests). Residual (P1): the backend tokenizes the *client-substituted* command, so a parameter with an unbalanced quote could split into extra literal args (harmless without a shell) — robust per-parameter server-side substitution from raw params would remove even that. *(2026-07-09)*
- **Multi-tenancy route scoping + JWT fail-fast + dev-JWT rotation** (third P0 blocker done): the task API previously ran as a single hardcoded `cli_user_placeholder` and, worse, its by-id routes looked tasks up by `id` alone — so any authenticated caller could **list every user's tasks** (`GET /tasks` had no `where`), and read/patch/delete/**run** *anyone's* task by guessing an id (IDOR → the run path is remote command execution on another user's agent). Every task route now derives `userId` from the verified JWT (`req.user.id`, via the already-mounted `authenticateToken`), and all lookups are owner-scoped: `GET /tasks` filters `where:{userId}`; `PATCH`/`DELETE`/`POST /:id/run` use `findFirst({id, userId})` (404 on a miss); `GET /:id/executions` confirms task ownership before returning logs; create/native/health/sync/discover and the template **apply** route all attribute to the token user. Backend now **fails fast on a missing/weak `JWT_SECRET`** (the `|| 'fallback-secret'` default — which would have let anyone forge a token — is gone; `>= 16` chars required at boot, alongside the existing agent-secret and encryption-key checks). The **committed dev JWT was removed** from `frontend/src/api.ts` (a real leaked credential) and replaced with an env-sourced `VITE_DEV_TOKEN` (gitignored `.env.local`, no committed fallback; demo mode never calls the backend so needs none), and **`JWT_SECRET` was rotated**, invalidating that leaked token. Added `.env.example` for both backend and frontend documenting every var. Templates stay a shared seeded catalog (global read is intentional — it's the curated library, all seeded under the placeholder user); route-level IDOR regression tests are folded into the pending real-Postgres integration suite (P1). Verified: backend typecheck + 83 tests, frontend typecheck + 40 tests, no committed token remains in tracked files. Remaining P0: per-OS structured command handling. The **git-history secret scrub** (the old token still lives in past commits, though rotation already killed it) is tracked under Go-public. *(2026-07-09)*
- **Encrypt `PlatformConnection.config` at rest** (second P0 blocker done): the connection `config` column (which holds API keys, agent IDs, and pairing secrets) was stored as plaintext JSON — a DB dump or backup leaked every credential. It's now encrypted at the application layer with the existing (tested) AES-256-GCM helpers, funneled through a single new module (`backend/src/auth/connectionConfig.ts`): `serializeConfig()` on the way in (write), `deserializeConfig()` on the way out (read). The Prisma column stays `Json`; the encrypted payload is stored as a JSON *string* in the canonical `iv:tag:ciphertext` form, and because encrypted configs are always strings while legacy configs were always objects, the stored JS type disambiguates the two — **legacy plaintext rows keep working with no migration** while every new write is encrypted. All 6 read sites (`createTask`/`applyTemplate`/`getHealth`/`syncTasks`×2/`runTask` across `routes/tasks.ts` + `routes/templates.ts`) and both write sites (the TASKHUB_NATIVE auto-provision in `index.ts` and the Windows auto-init in `/health`) now go through the helpers — no route touches `connection.config` directly, and the stale "*In a real system, we'd decrypt the config here*" comment is gone. A tampered/wrong-key payload throws (GCM auth failure is surfaced, not swallowed). Importing the module also gives the backend **fail-fast on a missing/short `ENCRYPTION_KEY`** at boot (the key must be exactly 32 chars). Verified: backend 83 tests (was 78; +5 new `connectionConfig` cases — round-trip, empty config, legacy-plaintext passthrough, null/undefined, tamper rejection). Remaining P0: multi-tenancy route scoping + dev-JWT rotation, per-OS structured command handling. *(2026-07-09)*
- **Agent WebSocket authentication** (first P0 blocker done): the agent↔backend Socket.IO channel — previously unauthenticated, so any process reaching port 3000 could drive `task:create`/`task:run` = RCE on the user's machine — is now authenticated on both ends. Backend `io.use()` middleware (`backend/src/ws/agentAuth.ts`) verifies an HMAC-SHA256 handshake over `(agentId, nonce, ts)` against a shared `AGENT_PAIRING_SECRET` (120s freshness, constant-time compare) and **rejects unauthenticated sockets before the connection handler runs**. State-changing commands are signed with a **per-session key** derived from the handshake nonce; the .NET agent (`AgentAuthenticator.cs`) verifies every `task:run`/`task:create`/`task:set_status` and drops anything with a bad signature or stale timestamp. Socket.IO CORS restricted to `ALLOWED_ORIGINS` (empty by default — only the non-browser agent connects today). Agent config (`TASKHUB_SERVER_URL` WSS-capable, `TASKHUB_PAIRING_SECRET`, `TASKHUB_AGENT_ID`) resolves from env **or** a gitignored `agent/TaskHub.Agent/appsettings.json` (env overrides the file; `appsettings.example.json` is the committed template, copied beside the published exe so no secret needs re-exporting each run); backend fails fast without a strong pairing secret. A shared cross-language HMAC golden vector is asserted by both the backend (Vitest) and agent (xUnit) suites so the two can't drift. A multi-agent code review also caught and fixed: an unauthenticated-frame crash in the agent's `task:run` handler (parse now inside the try), a reconnect race where a stale socket's late `disconnect` unregistered the live one (now guarded by socket identity), and added a server-side handshake **nonce replay cache** (a captured handshake can't be replayed within the freshness window to displace the agent). Verified: backend 78 tests, agent 39 tests; the Windows **auto-start / self-heal scheduled task** (`\Task-Hub\TaskHubAgent` → `Start-TaskHub.ps1`) was re-published and validated end-to-end — the published agent authenticates from its bundled config and the Windows connector reports `HEALTHY`, with the 10-min idempotent launcher confirmed not to spawn duplicates. **Breaking** — live agents must be rebuilt with the secret configured. Remaining P0: encrypt `PlatformConnection.config` at rest, multi-tenancy route scoping + dev-JWT rotation, per-OS structured command handling. Documented residuals (on-path attacker on plaintext transport only — mitigated by WSS, which the agent now supports): per-command replay within the 120s window, `task:create`'s `trigger` not covered by the signature, and a narrow shared-`SessionKey` reconnect false-reject. *(2026-07-09)*

## Strategy guardrails (from the 2026-07-07 analysis)

- **Reliability control plane, not universal scheduler** — two excellent connectors beat six half-connectors; new connectors unlock only when sync reliability >95% and crash rate <2% hold.
- **No fake data in the UI** — an automation tool earns trust by telling the truth (status panels, upvotes, dates).
- **Dogfood**: migrate real Task Scheduler jobs onto TaskHub-created tasks; every friction point is roadmap input.
